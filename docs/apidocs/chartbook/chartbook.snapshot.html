chartbook.snapshot#

Snapshots: what one commit of a pipeline built, kept in the store.

A pipeline is worked on while other pipelines depend on it. So the others never read its folder. They read a snapshot: every asset the pipeline declares, as it was built at one commit, copied into the store and labelled with that commit.

A snapshot is made on purpose, by whoever works on the pipeline, when its build is ready for others::

$ chartbook snapshot
ftsfr/fed_yield_curve at 4f2a91c: 3 assets in the store
Snapshot made. A pipeline that depends on this one gets it with `chartbook update`.

Three rules, decided by the maintainer on 2026-10-13 (docs_src/design/overview.md, “The snapshot model”):

  • Everything in the pipeline’s folder must be committed first. The label says “this is what that commit built”, and with uncommitted changes it would not be true.

  • It is not made by every build. Declaring a build ready is a decision, and the store changes slowly and on purpose.

  • Nothing else reads the folder. :mod:chartbook.lock pins from a snapshot, and a pipeline’s working directory can be in any state.

The same commit can have several snapshots. A pipeline that pulls data from outside gives other bytes on another day, with no file changed, so a snapshot has the time it was made, and the newest is the one a pin moves to. A snapshot that would be the same as the one before it is not made.

Where they are kept::

~/.chartbook/store/
  pipelines/
    ftsfr+fed_yield_curve/                 the pipeline
      2026-10-13T182205Z_4f2a91c0e1b2/     when it was made _ its commit
        _data/treasury_rates.parquet       what is new in it, in its place
        _chartbook/snapshot.json           the record

A record is JSON in the index’s format, like a lockfile: an envelope and one record for each asset, each with its content hash, and, for each of its files, where the store keeps it (stored): each file is kept once in the pipeline’s folder, in the first snapshot that had it (:class:chartbook.store.PendingSnapshot). A snapshot keeps what it names from being cleared (:func:chartbook.lock.plan_gc).

Clearing old ones. Every snapshot is kept until chartbook store gc is run, and then one is kept if a lockfile pins it, if it is the newest of its pipeline, if a label in that pipeline’s manifest points at a model version in it, or if it was made in the last :data:KEEP_DAYS days (:func:plan_removals). The rest may be removed, and the command asks first. Beside each pipeline’s records the store notes the folder they were made from (origins), which is how it finds that manifest.

A snapshot is found by commit, and a commit is the same in every clone of a repository. So one made in a folder is found by a pipeline that depends on that folder, and by one that depends on the same repository by URL.

Made by chartbook snapshot, a snapshot takes its owner’s word that what is on disk was built by that commit. chartbook run --snapshot builds and then makes one in the same command, and the record says so (built_with.run).

What a snapshot says, and what it does not. Which data it is: the hash of every file, which is complete. Which code made it: the commit. And a short note of the conditions it was made under (built_with, and inputs: what the pipeline itself was pinned to), which is there to explain a difference between two snapshots, not to make a build repeatable. Nothing of a pipeline’s .env is ever copied: it holds secrets, and a store is something to share.

class chartbook.snapshot.Snapshot[source]#

What one commit of a pipeline built.

Attributes: pipeline: The pipeline’s own ID when the snapshot was made. commit: The commit it was built from. subdirectory: The pipeline’s folder in its repository; empty at the top. made_at: When it was made, in UTC, to the microsecond: 2026-10-13T18:22:05.123456Z. With the commit, it is what names the snapshot. assets: A record for each asset the pipeline declared, by the asset’s reference within the pipeline (treasury_rates, chart/curve_today). One with a content_hash was built. path: The record’s file, if it has been written. built_with: A note of the conditions it was made under: whether the build ran in the same command (run), how its lineage was checked (lineage: pins or deep), and the versions of ChartBook and Python and the platform. It explains a difference; no hash covers it. inputs: What the pipeline itself was pinned to when the snapshot was made: the dependencies of its own lockfile, each with its commit and its pinned_hash. Empty if it has no lockfile. repository: The repository it was made in, as the web address of its origin remote (no credentials); empty when it has none. A dependency named by its ID alone keeps to the repository it was first pinned from. first_commit: The first commit of the repository it was made in, from its current commit back by first parents: the same in every full clone, with a remote or none, under any URL. Empty for a shallow clone, which does not have it. With repository, it is how a dependency named by its ID alone tells one repository from another. tags: The git tags on its commit when it was made: the names of that version, as git tag gave them. A tag made later is not in it. For people and pages; store gc asks git for tags. labels: The labels the pipeline’s manifest gave its models’ versions when the snapshot was made, by the model’s reference: {"model/x":         {"champion": "7f3a9c2e41b0"}}. Labels travel with snapshots so that a machine that cannot read the folder they were made from, a store a team shares, still knows which versions to keep; and so that a pipeline that depends on this one can pin this:model/x@champion without reading its folder. index: The pipeline’s own index at this commit, in the published form, as an object in the store: {"content_hash": …,         "size_bytes": …}, the object holding one index.json. It is what a docs build of the folder would have written just before the snapshot was made, so the data dictionary of this version is kept with its data. None for a snapshot made before snapshots carried it. documents: The files a writer needs that are not assets, as one object in the store: the manifest, the lockfile, the README, the write-ups, the pipeline’s own site pages, its logo and favicon, each under its path in the pipeline’s folder, and only those git tracks. {"content_hash": …, "size_bytes": …,         "files": [...]}. With the assets, they are enough to lay the version out as a folder and build its site (:func:materialize). None for a snapshot made before. stored: Where the store keeps the files of what it holds, as its record says: {"records": {name: …}, "index": …, "documents":         …}, each as :attr:chartbook.store.StoredObject.stored has it. Kept apart from the records, which a lockfile copies.

chartbook.snapshot.asset_record(ref: chartbook.refs.AssetRef, pipeline: str, declared_path: str, content, single: bool, keep: bool = False, reading: Optional[dict] = None) → dict[source]#

An asset as a snapshot and a lockfile record it; with its hash if stored.

This is the one place that shape is written.

Parameters:

  • ref – The asset’s reference, qualified with the pipeline’s name.

  • pipeline – That name.

  • declared_path – The asset’s path as its manifest gives it.

  • content – What was stored: its hash, its size and its files; or None for an asset that is declared and not built.

  • single – Whether the asset’s path named one file. A directory has its files listed, as the index lists a directory model’s: files is what tells a directory from a file.

  • keep – Whether the manifest marks the asset keep = true: every version of it is kept in the store (docs_src/design/keep.md). Written only when it does.

  • reading – A dataframe’s format and read_options, as its manifest gives them (:func:chartbook.formats.declared), kept in its location so that a pipeline that reads the pin reads the bytes as their owner said to. Written only when given.

chartbook.snapshot.lineage_gaps(directory: Union[str, pathlib.Path], store: Optional[chartbook.store.Store] = None) → list[str][source]#

What stands between a pipeline’s pins and its full lineage, one line each with what to run; empty if nothing.

A snapshot records what its pipeline was pinned to (inputs: each dependency’s commit and the hash over its pins), and the assets it holds were made from those bytes. So first the check chartbook pin --frozen makes (:func:chartbook.lock.verify): a lockfile, every dependency in it, pinned from where the manifest says, its bytes in the store. Then, for a path dependency something was pinned from: that its pin names a snapshot, by its commit and time, that the store has that snapshot and it holds each asset pinned from it under its name at its hash, and that each label pinned names a version some snapshot of the pipeline holds; so that a lockfile changed by hand, or brought from another store, is caught. (A git dependency is pinned from its clone, not a snapshot, and its hashes are checked only to be in the store.)

Nothing that could not have been read is a gap: an asset the other pipeline had not built when it was pinned, and a dependency of which nothing is pinned (it declares nothing, or has no snapshot yet). Reads that do not go through the lockfile (a load through a catalog, a model version named by its hash) are not seen here.

Raises:

  • LockError – If the lockfile is there and cannot be read.

  • ValueError – If the manifest’s [dependencies] is malformed.

chartbook.snapshot.plan_removals(store: chartbook.store.Store, pinned: set[tuple[str, str]], hashes_of_missing: set[str] = frozenset(), keep_days: float = KEEP_DAYS, now: Optional[datetime.datetime] = None, keep_lineage: bool = False, aggressive: bool = False, hashes_elsewhere: set[str] = frozenset(), hashes_noted: set[str] = frozenset(), noted: Optional[dict] = None, labelled: Optional[dict] = None) → chartbook.snapshot.SnapshotPlan[source]#

Say which snapshots may be removed. Nothing is removed.

A snapshot is kept if, in this order:

  1. a lockfile pins it (its commit and time are named by a dependency);

  2. a note of a lockfile pins it: one that cannot be found, one on another machine, or one read here whose note, from its last pin, names it (noted); or, for a note from before notes named their snapshots, it is the newest snapshot holding one of the objects the note names; 2b. a lockfile, or a note of one, pins a model version by its label (rates:model/m@champion), and this is the newest snapshot of that pipeline holding the version (labelled): a label resolves to a version an older snapshot holds, which the pinned moment alone would not keep, and a dependant’s next snapshot needs it;

  3. it is the newest snapshot of its pipeline, or the newest that a branch or a tag of the repository it came from can pin from;

  4. a label points at a model version it holds: in the pipeline’s manifest, read from the folder the snapshots were made from, or as recorded in the newest snapshot of the pipeline (:func:labels_of); 4b. it is the newest snapshot holding a version of an asset the manifest marks keep = true (:func:keeps_of, read as labels are: from the folder, or from the newest snapshot’s records): every version of such an asset is kept, with aggressive or without, since the mark is a cost and not a name (docs_src/design/keep.md); each is in

    attr:

    SnapshotPlan.kept_versions;

  5. it was made in the last keep_days days, or is dated after now by less than that, as a snapshot made on a machine whose clock is ahead is; one dated further ahead is removed if nothing pins it;

  6. with keep_lineage: a snapshot kept for any of these reasons was made from it, or from a label pointing into it, and so on up, so that a kept snapshot’s lineage stays whole (:func:_keep_lineage). Without it, which is the default, a store keeps what work needs now and lets old lineage go; chartbook lineage then says a snapshot upstream is not in the store.

With aggressive, names keep nothing: 3 is only the newest of the pipeline, never the newest a branch or tag can pin from, and 4 is not asked at all, so a tagged version, or a labelled model version, goes once nothing else keeps it.

Otherwise it may be removed. What it names and nothing else names is then removed with it, by :func:chartbook.lock.plan_gc.

Parameters:

  • pinned – The (commit, made_at) pairs that readable lockfiles pin.

  • hashes_of_missing – The objects named by lockfiles that cannot be found and are not to be forgotten.

  • hashes_elsewhere – The objects named by lockfiles on other machines, which are not read here, and by notes from before notes named their machine, or copies of notes.

  • hashes_noted – The objects the notes of lockfiles that were read recorded at their last pin, which the lockfile may no longer name (after a pull, or a switch of branch): a note only adds.

  • noted – The snapshots notes record, (commit, made_at), each with why it is kept. The three sets of objects above are for notes that record no snapshots.

  • labelled –

    The model versions lockfiles and notes pin by label, each (commit, made_at, name, content_hash) as

    meth:

    chartbook.lock.Lock.labelled gives them, with why each is kept. The version is looked for among the snapshots of the pipeline the moment names; among every pipeline’s where the moment names none the store has.

Raises:

SnapshotError – If a record cannot be read.
