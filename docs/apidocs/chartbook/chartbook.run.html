chartbook.run#

Running a script in a pipeline.

A pipeline names its commands in [scripts]. build is the one that makes its assets current, and it is usually one word: doit, make, snakemake. That tool decides what inside the pipeline is out of date::

$ chartbook run
ftsfr/rate_forecast: pinning what it depends on
ftsfr/fed_yield_curve: 3 pinned
Wrote chartbook.lock.
ftsfr/rate_forecast: build

chartbook run builds the pipeline it is run in. First it sees that what the pipeline depends on can be read, and it does that without ever touching another pipeline’s working directory:

  • It never builds in a folder the pipeline depends on. A path dependency is a directory somebody works in. They may be half-way through a change. This pipeline reads what is pinned, not what is there, so running that folder’s build would disturb its owner and change nothing this pipeline reads. It is its owner’s to build.

  • A git dependency is built once, in a clean copy. Nobody works in ChartBook’s own copy of a commit, so there is nothing to disturb. The build runs in a writable copy of the checkout (:meth:chartbook.gitcache.GitCache.work_copy), which is how data that a repository builds and does not commit comes to be there to pin. It is built once for a commit. force builds it again, which is how data that is pulled from outside is refreshed on purpose.

  • What has no pin yet is pinned, just before the build, so the pipeline’s code can read it. A pin that exists is never moved. chartbook update is the only thing that moves one.

In a catalog, the script is run in each of the catalog’s pipelines, one that another of them depends on first.

This is not a task runner. There is one string per script name, no dependencies between scripts, no retries, no schedule and no history. See “Running things” and “Not doing” in docs_src/design/asset-graph.md, and “The snapshot model” in docs_src/design/overview.md for why a pipeline is never built from the outside in.

chartbook.run.build_tool_runs_chartbook_build(directory: Union[str, pathlib.Path], command: Optional[str] = None) → Optional[tuple[str, int, str]][source]#

A line of a pipeline’s build tool’s own file that runs chartbook build: the file, the line number, what it runs.

Before 0.2.0, chartbook build rendered the site, and a dodo.py task said chartbook build -f to do it. Now chartbook build runs the pipeline’s build command first, which is that same build tool. Only the task file of the tool command runs is read: dodo.py for doit, a Makefile for make, a justfile for just (each, with command None). What is not run is not taken: a comment, a docstring, a chartbook build --project-dir of another pipeline.

Parameters:

command – The pipeline’s build command, as [scripts] build says it.

Returns:

The first such line, or None.

chartbook.run.execute(script: str, directory: pathlib.Path, name: Optional[str] = None, foreign: bool = False) → int[source]#

Run one script in a directory, and return its exit code.

The script is handed to a shell whole, so a value of several lines is one script: what one line sets up, the next can use. It stops at the first command that fails. Its output goes where this process’s does.

The shell is bash where there is one, because that is what an module load or a conda activate expects, and sh otherwise. On Windows it is cmd: one line is run as it is, and several go in a batch file that stops at the first line that fails, with its exit code (:func:_batch_script).

Parameters:

  • name – The script’s name in [scripts]. With it, the script is told which pipeline and which script it is (:func:running).

  • foreign – Whether the directory is a git dependency’s working copy, the cache’s: then git in the script is not told of any other repository the environment names (a git hook’s GIT_DIR).

Returns:

The script’s exit code. One that a signal stopped gives 128 plus the signal’s number, as a shell reports it.

chartbook.run.kept_missing(directory: Union[str, pathlib.Path], store: Optional[chartbook.store.Store] = None) → list[source]#

The assets a pipeline marks keep = true that are not on disk while a snapshot in the store holds them.

For each: its reference within the pipeline, its path as declared, and the newest snapshot of the pipeline holding its bytes, in the store and whole (:func:chartbook.snapshot.newest_holder). This is the one moment a build would make a costly asset again that could be put back instead (docs_src/design/keep.md): an asset no snapshot holds has to be made, and nothing is said of it. A pipeline that is not in git has no snapshots, and a shallow clone sees only the commits it has.

Raises:

ValueError – If the manifest cannot be read.

chartbook.run.plan(project_dir: Union[str, pathlib.Path] = '.', git_cache: Optional[chartbook.gitcache.GitCache] = None, git: bool = True, force: bool = False, store: Optional[chartbook.store.Store] = None) → list[chartbook.run.Step][source]#

Say which pipelines a run is about, in order.

That is the pipeline in project_dir, or every pipeline of the catalog there, each after any other of them that it depends on. With git, it is also their git dependencies, each before what depends on it: a git dependency is fetched if it has to be and given a working copy, which is the only thing here that changes anything.

A path dependency is never in the order. It is a folder somebody works in, and it is theirs to build.

A git dependency that is built already is in the order, marked as built, and what it depends on is left out: that was needed to build it, and it is built. With force it is gone into all the same.

Parameters:

  • project_dir – A pipeline’s directory, or a catalog’s.

  • git_cache – Where git dependencies are fetched to; this user’s by default.

  • git – Whether git dependencies are in the order.

  • force – Whether to go into a git dependency that is built already.

  • store – The store, which says which dependencies named by their ID have no snapshot and so are built from the default host; this user’s by default.

Returns:

The pipelines, each after what it depends on.

Raises:

  • RunError – If project_dir holds no manifest, or two of a catalog’s pipelines depend on each other.

  • ValueError – If a manifest cannot be read, or its [dependencies] or [scripts] is malformed.

chartbook.run.run(project_dir: Union[str, pathlib.Path] = '.', script: str = BUILD_SCRIPT, store: Optional[chartbook.store.Store] = None, git_cache: Optional[chartbook.gitcache.GitCache] = None, echo: Callable[[str], None] = print, on_pin: Optional[Callable] = None, force: bool = False, snapshot: bool = False, frozen: bool = False, on_verify: Optional[Callable] = None, on_snapshot: Optional[Callable] = None, remake: bool = False, remake_command: str = 'chartbook run --remake') → chartbook.run.RunReport[source]#

Run a script in a pipeline, or in every pipeline of a catalog.

For build, two things are done first. A git dependency that has not been built at its commit is built, in its working copy. And each pipeline’s dependencies are pinned before its own script runs: what has no pin yet is pinned, and no pin is moved.

Nothing is ever run in a path dependency’s directory. Any other script is run only where it was asked for.

The pipeline that was asked for must have the script. A pipeline of a catalog that has no script by that name is passed over.

Parameters:

  • project_dir – A pipeline’s directory, or a catalog’s.

  • script – The script to run; build by default.

  • store – The store to pin into; this user’s by default.

  • git_cache – Where git dependencies are fetched to; this user’s by default.

  • echo – Called with each line that says what is being done.

  • on_pin –

    Called with a pipeline’s step and its

    class:

    chartbook.lock.PinReport after its dependencies are pinned.

  • force – Build a git dependency again even if it is built already. This is how data it pulls from outside is refreshed.

  • snapshot – After a pipeline’s build succeeds, make a snapshot of it (:mod:chartbook.snapshot): build, and declare the build ready, in one command. Everything in its folder must be committed before the build starts and still be when it ends. The snapshot records that the build ran in the same command.

  • on_snapshot –

    Called with a pipeline’s step and its

    class:

    chartbook.snapshot.SnapshotReport after its snapshot is made.

  • frozen – Write nothing before the build but, where the store can be written, its note that this machine reads these pins (:func:chartbook.lock.note_this_machine): no pin, no fetch, no lockfile, no object. Instead check that the lockfile is complete and every pin is in the store (:func:chartbook.lock.verify), and refuse to build if not. A git dependency is not built either; its pins have to be there. For CI, and for a store one may only read.

  • on_verify –

    Called with a pipeline’s step and its

    class:

    chartbook.lock.FrozenReport, under frozen.

  • remake – Run build even though an asset the manifest marks keep = true is not on disk while the store has a version of it. Without it, that stops the command before anything is built, since the build would make the costly asset again (:func:kept_missing, docs_src/design/keep.md).

  • remake_command – The command line that says remake, for the message: chartbook build --remake from chartbook build.

Returns:

What was run, and what failed if anything did.

Raises:

RunError – If the pipelines cannot be put in an order, the one asked for has no such script, or a kept asset is missing while the store has it and remake is not set.

chartbook.run.running(directory: Union[str, pathlib.Path], script: str) → bool[source]#

Whether this process is inside that script of that pipeline.

A build script that calls chartbook build or chartbook run in its own pipeline would be run by the command it calls, without end; so would two pipelines whose build scripts each run the other’s. Every script ChartBook is running is in :data:RUN_STACK_ENV_VAR, and a pipeline anywhere in it is one this process is already inside.
