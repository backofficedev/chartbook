chartbook.stores.s3#

A store in an S3 bucket: [store] url = "s3://bucket/prefix".

Needs boto3, which pip install chartbook[s3] installs. The bucket is laid out exactly as a folder store is, under the prefix: store.json, objects/sha256/<2>/<62>/<file>, roots/<note>.json and snapshots/<commit>/<pipeline>/<stamp>.json. So aws s3 sync of a folder store into a bucket is this store, and back.

Readers open files, so what they read is a local copy: :meth:S3Store.get downloads an object’s files once into a cache folder on this machine, laid out as a folder store too, checks that they hash to the object’s name, and returns that folder. Each read while online is one listing request, which is how a name another pipeline added for the same bytes is seen; offline, an object that was read and checked before is served from the cache. Nothing else in ChartBook changes for a store that is remote; data.path() gives the path of the cached copy.

Credentials are the AWS SDK’s own: the environment, ~/.aws, an instance role. The URL never carries them. It may say where the service is, for a bucket that is not at AWS::

s3://bucket/prefix?endpoint=https://minio.example.org&region=us-east-1

A store that is read-only for this machine (s3:ListBucket and s3:GetObject) serves chartbook pin, chartbook run --frozen and data.load(); what would write raises :class:~chartbook.store.ReadOnlyStoreError and says what was refused. Writing needs s3:PutObject, and store gc s3:DeleteObject.

One thing the folder store does that this one cannot: make an object appear whole or not at all. Files are uploaded one by one, so a snapshot interrupted while uploading an object of several files leaves a partial one, which has() reports (a listing cannot tell). What tells is the record: :meth:S3Store.incomplete compares the keys under the object and their sizes with the files and sizes the record gives, as the folder store compares a synced folder’s files, so pin, update, pin --frozen and a read all say the object is not fully uploaded yet; get() refuses one whose files do not hash to its name. Making the snapshot again uploads what is missing and completes it.

Why an object is not whole as its record has it, by the keys under it and their sizes; None if it is.

Files are uploaded one at a time, so a snapshot interrupted while uploading an object of several files leaves some of its keys missing, and one being made now has them arriving. The sizes the listing gives are compared with the record’s, as the folder store compares a synced folder’s files (:func:chartbook.store.unsynced_part); one listing request, and nothing is downloaded. Offline, an object this machine downloaded and checked before is whole.

Copy what a declared path names into the cache, hash it, and upload it.

links is read for its errors only: a remote store holds copies, whatever was asked for, so the object never changes when the original does. An object the bucket already has is written again in metadata only, so that it counts as stored now and gc does not take it from under a pin in progress.
