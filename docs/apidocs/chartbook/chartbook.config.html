chartbook.config#

Settings: where this machine keeps things, read in layers.

Three files, and the environment above them:

  • the user’s ~/.chartbook/settings.toml;

  • the organization’s system-wide file, /etc/chartbook/settings.toml on Unix and macOS, %ProgramData%\chartbook\settings.toml on Windows, or the file CHARTBOOK_SYSTEM_SETTINGS names;

  • the defaults under ~/.chartbook.

Each layer is consulted only where the one above it is silent, key by key, so an organization sets the store once for every machine and a user keeps their own choices for everything else::

~/.chartbook/
├── chartbook.toml       # the global catalog (optional)
├── settings.toml        # the user's settings
├── sources.toml         # the machine's urls and credentials for [sources]
├── trust.toml           # the pipelines and repositories this user trusts a build of
├── machine-id           # what names this machine in a store's notes of lockfiles
├── store/               # the store, unless settings say otherwise
├── cache/               # what was read from a remote store
└── git/                 # clones of git dependencies

[store] url says where the store is: a folder (a bare path or file:///), an S3 bucket (s3://bucket/prefix, with pip install chartbook[s3]), or another kind of store a plugin provides, by its scheme. CHARTBOOK_STORE overrides it. [git] path and CHARTBOOK_GIT_CACHE do the same for the git cache, [cache] path and CHARTBOOK_CACHE for the cache of a remote store; [catalog] path names the default catalog. Which store a machine uses is never a fact about a pipeline, so none of this is in a chartbook.toml.

chartbook.config.get_cache_path() → pathlib.Path[source]#

Get the directory a remote store’s objects and records are kept in once read.

A store in a bucket is read through a copy on this machine, laid out as a folder store under a folder for that bucket and prefix (:mod:chartbook.stores.s3). Resolution order:

  1. The CHARTBOOK_CACHE environment variable.

  2. cache.path from the user’s settings, then the organization’s (:func:read_settings).

  3. ~/.chartbook/cache.

The directory need not exist yet, and everything in it can be removed: it is read again from the store.

Returns:

Return type:

Path

Raises:

ValueError – If cache.path in the settings file is not a path.

chartbook.config.get_machine_id(create: bool = True) → str[source]#

The name this machine goes by in a store’s notes of its lockfiles.

A store keeps a note of each lockfile whose pins it keeps, and a path names a file on one machine only: one person’s two machines can each have a lockfile at the same path. So a note names its machine too.

The name is made at random the first time a note is written, and kept in ~/.chartbook/machine-id beside what the operating system calls the machine (:func:_os_machine_identity, as a hash). A home folder that comes to another machine (copied by a migration or restored from a backup, shared by several computers, kept by a sync service) does not bring its name with it: that machine makes one of its own, kept in the same file. So does a cloned virtual machine or an image that had pinned, when its operating system made its identity anew. One that did not (/etc/machine-id cloned, Windows without sysprep), with a copied home, has the same name as the machine it was cloned from, and the two are not told apart: each lasting machine needs an identity of its own, or a CHARTBOOK_MACHINE_ID of its own. Nothing else (the host name, a hardware address) tells machines apart, as one machine’s may change. Where nothing can be kept, or there is no home folder, a name made from what the operating system calls the machine is used.

CHARTBOOK_MACHINE_ID names it instead: for machines that come and go with a fresh home folder each time (CI runners, containers), so that each one’s notes replace the last one’s rather than pile up. Two machines that last must never be given one name: each would read the other’s lockfiles as its own.

Parameters:

create – Whether to make the name if there is none yet. Without it, the name used where nothing can be kept is given, which only a machine that could not keep a name of its own wrote notes under.

chartbook.config.get_store_url() → str[source]#

Where the store is, as the settings say it: a folder, or a URL.

The store is a setting of the machine or the organization, never of a pipeline, so it is read in layers, each only where the one above it is silent:

  1. The CHARTBOOK_STORE environment variable, for one shell or one CI job.

  2. [store] url in the user’s ~/.chartbook/settings.toml.

  3. [store] url in the organization’s settings file (:func:get_system_settings_path).

  4. ~/.chartbook/store.

A bare path is a folder. file:// is a folder too. s3:// is a bucket, with pip install chartbook[s3]; another scheme names a kind of store a plugin provides. [store] path is still read, as a folder, with a warning. A relative folder in a settings file is relative to that file’s folder.

Raises:

ValueError – If the user’s settings file is faulty; a fault in the organization’s file is a warning, and that file is ignored.

chartbook.config.read_settings() → dict[source]#

The settings in force: the user’s over the organization’s, key by key.

Each layer is consulted only where the one above it is silent. Within a table such as [store], the user’s keys are added to the organization’s, so an organization can set the store for every machine and a user can still choose everything else. Each layer is put in order first (:func:_normalized): a deprecated spelling is read as the current one, and a relative folder is made absolute against the file it is in, so that a key the user set is never shadowed by the same setting spelled differently below it. The environment variables (CHARTBOOK_STORE, CHARTBOOK_GIT_CACHE) sit above both and are read by the functions that need them.

Raises:

ValueError – If the user’s file cannot be read or parsed, or a table in it is malformed; the message names the file.

chartbook.config.read_system_settings() → dict[source]#

Read the organization’s settings file, or {} if there is none.

A file that is named and not there, or that cannot be read or parsed, is reported with a warning and treated as absent: a fault in the organization’s file must not stop every command on the machine.

chartbook.config.read_trust() → list[source]#

The entries of the trust record (docs_src/design/trust.md), each a dict.

A [[pipeline]] entry has kind "pipeline", its path resolved, level, and id, repository and since as written (None when absent). A [[repository]] entry has kind "repository", its url as :func:chartbook.identity.repository_key reduces it, level and since.

The file is read as a settings file is: one that cannot be read stops the command, naming the file; an entry of another shape is passed over with a warning naming the file and the entry.

Returns:

The entries, in the file’s order; [] with no file.

Raises:

ValueError – If the file cannot be read or parsed; the message names the file.

chartbook.config.shown_store_url(url: str) → str[source]#

A store URL as it may be printed: with no user name or password in it, nor in a URL among its options.

s3://user:secret@b/p?endpoint=https://u:pw@minio.example.org is shown as s3://b/p?endpoint=…. A password may hold any character (half of AWS’s secret keys have a /; others a ?, an &, a #), so all up to the last @ of the URL goes, read as written (%40 is an @), and no option’s value is shown at all, since a password in one may hold what would end it. The options are what follows a ? that a name and an = follow. A path with no //host part (two backslashes on Windows) is as it is: a folder’s path may hold an @, as a Google Drive folder names its account.

chartbook.config.trust_of(folder) → Optional[str][source]#

How far a build of folder is trusted: "run", "render" or None.

The highest level among the entries of the trust record that cover the folder: a [[pipeline]] entry whose path is the folder or a parent of it, and a [[repository]] entry whose url is the repository the folder’s origin remote names (:func:chartbook.identity.repository_key; a folder with no remote matches none). Before the record:

  • a build of files from a store (CHARTBOOK_UNTRUSTED_SOURCE=1,

    func:

    untrusted_source) is never trusted, whatever the record says;

  • CHARTBOOK_TRUST=all trusts every folder at run; the variable takes no other value, and another is warned about once and ignored, so what follows applies under it as under no value at all;

  • under CI (the environment variable, set to anything), the checkout is trusted at run: a folder in the git repository the working directory is in, or in the working directory itself when it is in none.

What each level allows is in docs_src/design/trust.md.

Raises:

ValueError – If the trust record cannot be read.

chartbook.config.untrusted_source() → bool[source]#

Whether this build is of files that came from a store, not from a folder of the user’s.

Such a build uses no template from the project’s folder, copies only pages and pictures of its site folder, and lets no page take in a file from outside the site (docs_src/design/versioned-catalog.md).

chartbook.config.without_credentials(text: str) → str[source]#

A message with no user name or password of any URL or //host path in it: scheme://user:pass@ becomes scheme://.

For what an SDK or the system says, which may echo an address or a path it was given: an OSError names its file, and a store at //user:pass@host/share is one, as is the path Windows makes of it, which begins with two backslashes (four, in a message that quotes it). All up to the last @ of a line that has an address goes, since a password may hold a space or a quote.
