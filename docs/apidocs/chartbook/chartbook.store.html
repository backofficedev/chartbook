chartbook.store#

The store: a local folder of files named by the hash of what is in them.

The store is where a pinned copy of another pipeline’s asset is kept, and later where a build’s result is kept so that the same build need not run twice. An object in it is one asset, and its name is the asset’s content hash (:mod:chartbook.hashing), so the same bytes pinned by ten projects are one object.

::

~/.chartbook/store/
  store.json                                       which layout this is
  objects/sha256/7f/3a9c…/treasury_rates.parquet   an asset that is one file
  objects/sha256/b2/09e1…/year=2024/part-0.parquet an asset of many files
  builds/                                          a name kept free; nothing is written here
  roots/                                           the lockfiles that name objects
  snapshots/                                       what each commit of a pipeline built
  tmp/                                             objects being written

An object is a directory holding the asset’s files under their own names. That is why a path into the store still ends in .parquet, and why a partitioned dataset keeps folders like year=2024/.

What a store is, whatever holds it, is :class:Store: objects named by their content hash, the lockfiles that keep them, and the snapshot records. The folder store, :class:FolderStore, is the one that is built::

from chartbook.store import FolderStore

store = FolderStore("~/.chartbook/store")
stored = store.put("_data/treasury_rates.parquet")   # -> its hash
store.has(stored.content_hash)                       # True
store.get(stored.content_hash)                       # the object's directory
store.delete(stored.content_hash)

Another kind, an object store or a database, is a plugin: a class that provides the same methods, found by the scheme of the store’s URL in the entry-point group chartbook.stores (:func:store_for_url). The store is a setting of the machine, never of a pipeline; see

func:

chartbook.config.get_store_url.

The declared file never moves. put leaves path where it is and makes the object from it by the cheapest means the disk allows, tried in this order (:data:LINKS):

reflink A copy-on-write clone (APFS, btrfs, XFS). Costs nothing, and is the store’s own bytes: nothing outside the store can change it. hardlink A second name for the same file. Costs nothing, and is the original file: if that is later rewritten in place, the object changes with it. symlink A pointer to the original file. Crosses disks, changes whenever the original does, and dangles if the original is moved. copy A full copy. The store’s own bytes.

So an object made by reflink or copy is frozen, and one made by hardlink or symlink is frozen only for as long as the original is left alone or is replaced with a new file, never rewritten.

meth:

Store.verify is what tells: it hashes every object again and reports each whose content is no longer what its name says.

A snapshot (:mod:chartbook.snapshot) and pinning (:mod:chartbook.lock) are what put things in the store. A snapshot’s record is kept under snapshots/, and what it names is never cleared. Pinning leaves a note of each lockfile under roots/ so that clearing the store out never removes another project’s pins. The design is “The store” in docs_src/design/asset-graph.md.

A store in a synced folder. A folder that a sync service (Google Drive, Dropbox, OneDrive) keeps in step between machines is a store they share, and the service leaves two marks of its own in it. A file can be there before all of its bytes are: a record says how many an asset has (size_bytes), and :meth:Store.incomplete compares the sizes on disk with it, which costs no read. And a file changed in two places at once is kept twice, the second under a name of the service’s (20261017T163232.294414Z (1).json): records and origin notes are listed by the names a store gives them (:func:is_record_name), so such a copy is passed over; a copy of a note of a lockfile is read (:attr:Root.copy), as a note only ever adds to what is kept.

Note that a lockfile on this machine names these objects, and pins these snapshots, so that they are kept.

Called whenever a lockfile is written. One note is kept per lockfile and machine, and a later call replaces it. A note of the same path from before notes named their machine is left as it is: it may be another machine’s, and only a person can tell. In this user’s own store (:meth:is_users_own) it can only be this machine’s, and this note takes its place.

Machines are told apart by name only (:func:chartbook.config.get_machine_id): two that share one (a clone that kept its operating system’s identity, with a copied home) write one note per path.

Parameters:

  • lockfile – The path of a chartbook.lock.

  • hashes – The content hashes it names.

  • snapshots – The snapshots it pins, each (commit, made_at).

  • machine – The name to note it under: this machine’s by default; "" for the path alone, as notes were named before they named machines (a CI runner with no name of its own), which no note under a name then takes the place of.

  • labelled – The model versions it pins by label, each (commit, made_at, name, content_hash) (:attr:Root.labelled).

Raises:

ValueError – If one of hashes is not a content hash.

put(path: Union[str, pathlib.Path], links: Iterable[str] = LINKS) → chartbook.store.StoredObject[source]#

Store what a declared path names, and return its hash.

path is a file, a directory, or a glob, as in a manifest. It is left exactly where it is. The object is made beside it, by the first of links that the disk allows, and then hashed, so the name an object gets is the hash of what the store actually holds.

Storing the same content twice makes one object. Storing a file whose bytes are already there under another name adds the name.

Parameters:

  • path – An absolute path, which may contain glob characters.

  • links – The kinds of link to try, in order; see :data:LINKS. Pass ("reflink", "copy") for an object that must not change when the original does. If the store already holds this content as a link to a file outside it, the object is then replaced by one that is the store’s own.

Returns:

The stored object.

Raises:

  • FileNotFoundError – If nothing is at path.

  • StoreError – If no kind of link works, or the store’s layout is one this version does not know.

  • ValueError – If links names an unknown kind.

Attributes: content_hash: The asset’s content hash, sha256:<hex>, which is the object’s name. size_bytes: The total size of its files. path: The object’s directory in the store. files: Its files, as paths inside that directory with forward slashes, sorted. entries: For an asset of several files, each file with its own size and hash, as it was just stored. Empty for an asset that is one file. links: The kinds of link that were used to make it, in the order of :data:LINKS. Empty when the object was already there. created: True if this call made the object; False if the store already held it.

chartbook.store.declared_name(declared: str) → Optional[str][source]#

The name a declared file has inside its object: the last part of its path, / and \ both separating parts.

One rule for the three that must agree: :meth:Store.put, which names the file in the object; a record’s list of what a reader opens (chartbook.snapshot.files_read); and the reader (chartbook.resolve._held). A manifest written on Windows says _output\m.json, and the object holds m.json on every system; a file whose own name holds a backslash, which only POSIX allows, is stored under what follows it, so that it reads the same everywhere. None for a path of no name.

Whether a file is named as a store names a snapshot record.

A sync service that finds a file changed in two places keeps both, the second under a name of its own, 20261017T163232.294414Z (1).json. That copy is not a record the store wrote, and is passed over.

chartbook.store.on_disk(folder: pathlib.Path, parts: list[str]) → pathlib.Path[source]#

The file at these parts of a path under a folder, as the disk names it.

A name with a letter outside ASCII may be written in either of Unicode’s forms (é as one character, or as e and an accent), and a sync between macOS and Linux may hand a file over in the other: where the name as written is not there, a name equal to it under NFC is taken. An ASCII name is the same in both, and nothing is looked at.

chartbook.store.plain_parts(relative: str) → Optional[list[str]][source]#

The parts of a path inside an object, if it is a plain relative path; else None.

Plain: parts joined by single /, none empty, . or .., and no NUL; on Windows, also no backslash or colon, which it reads as a separator or a drive (elsewhere they are ordinary characters of a name, and an object may have a file named with them, part-2024-01-01T00:00). A record or a key may come from anyone who can write to a store, and a reader makes a path of each.

chartbook.store.this_node() → str[source]#

The hardware address of one of this machine’s network interfaces, as twelve hex digits; empty if it has none to give.

For a person to read in a note, beside the host name: nothing goes by it, since one machine’s may change (another interface, a dock, a restart). Asked only when a note is written. chartbook.store.unsynced_part(path: pathlib.Path, size_bytes: int, files: Optional[dict] = None, every: bool = False, content_hash: str = '') → Optional[tuple[str, bool]][source]#

What of an object’s folder is not as its record gives it, in a few words; None when nothing is.

files are the files a reader opens, by their path in the object, each with its size, as the record gives them: the one file of an asset that is a file, under its own name (the object may hold the same bytes under other names too, which are other pins’ business), or each file of a directory, which are then every file of it. Without them, as for a glob, the files the object holds are summed, as they were hashed; so they are when the one file named is not in it and what it holds is not those bytes under other names (by size, and for that rare case by the hash of one, against content_hash), as a directory pinned before records listed its files, which a reader reads as the folder.

A file that is a link is no sync’s doing, and is not judged here:

Meth:

Store.verify and a reader’s own checks see to it. Only sizes and names are looked at, but in that rare case.

Returns:

What is wrong, and whether a sync that has not finished would explain it (False for a file the record does not list, a sync service’s copy most likely, which waiting does not mend).
