chartbook.store#

The store: where the snapshots of pipelines are kept, each file once.

A pipeline’s data is read by other pipelines from the store, never from its folder. What a pipeline has built is put there by chartbook snapshot, and what a pin takes from another repository by chartbook pin. The store’s layout is made to be read by a person as well::

~/.chartbook/store/
  store.json                                which layout this is
  pipelines/
    ftsfr+fed_yield_curve/                  one folder per pipeline (pipeline_folder)
      2026-10-12T091500Z_4f2a91c0e1b2/      a snapshot: when it was made _ its commit
        _data/treasury_rates.parquet        the pipeline's files, in their own places
        _chartbook/snapshot.json            the record, and the dictionary of every file
      2026-10-26T182205Z_9b1e22d7a0c4/      a later one: only what is new or changed
    +unowned/7f3a9c…/rates.parquet          an object no pipeline owns
  origins/                                  the folders snapshots were made from
  roots/                                    the lockfiles that pin what is here
  tmp/                                      what is being written

Each file is kept once in its pipeline’s folder, in the first snapshot that had it. A later snapshot’s folder holds only what is new or changed, and its record says, for every file of every asset, its hash, its size and the snapshot that keeps it (kept_in). The record is written last, so a folder without one is never taken for a snapshot, and nothing in the store is moved or rewritten once written: only store gc removes. That is what makes a store in a synced folder, a bucket, and a pipeline’s folder copied by hand into another store safe. The design is docs_src/design/plan-0.3.0.md.

An asset is still named by its content hash (:mod:chartbook.hashing): one file’s, or the hash of the listing of its files. A reader asks for it by that hash (:meth:Store.get) and is handed a folder with its files under their own names, so a path into the store still ends in .parquet and a partitioned dataset keeps folders like year=2024/: the snapshot’s own folder where it holds the asset whole, else a view in this machine’s cache that gathers the files from where they are kept.

What a store is, whatever holds it, is :class:Store. The folder store,

class:

FolderStore, is the one every install has::

from chartbook.store import FolderStore

store = FolderStore(“~/.chartbook/store”) pending = store.begin(“ftsfr/fed_yield_curve”, commit, made_at, base=pipeline_folder) stored = pending.put(pipeline_folder / “_data/treasury_rates.parquet”) pending.write(record) # the snapshot, last store.get(stored.content_hash) # a folder holding the file

Another kind, an object store or a database, is a plugin: a class that provides the same methods, found by the scheme of the store’s URL in the entry-point group chartbook.stores (:func:store_for_url). The store is a setting of the machine, never of a pipeline; see

func:

chartbook.config.get_store_url.

The declared file never moves. A snapshot’s file is the store’s own bytes: a copy-on-write clone where the disk allows (reflink: APFS, btrfs, XFS), else a copy, so nothing outside the store can change it. The other two kinds of :data:LINKS, a hard link and a symlink, are for reading: a view in the cache is made of links into the store.

meth:

Store.verify hashes every file again and reports each that is no longer what its record says.

Pinning leaves a note of each lockfile under roots/ so that clearing the store out never removes another project’s pins.

A store in a synced folder. A folder that a sync service (Google Drive, Dropbox, OneDrive) keeps in step between machines is a store they share, and the service leaves two marks of its own in it. A file can be there before all of its bytes are: a record says how many each file has, and :meth:Store.incomplete compares the sizes on disk with it, which costs no read. And a file changed in two places at once is kept twice, the second under a name of the service’s (snapshot (1).json): a record is read under its own name only, so such a copy is passed over; a copy of a note of a lockfile is read (:attr:Root.copy), as a note only ever adds to what is kept.

add_root(lockfile: Union[str, pathlib.Path], hashes: Iterable[str], snapshots: Iterable[tuple[str, str]] = (), machine: Optional[str] = None, labelled: Iterable[tuple[str, str, str, str]] = ()) → None[source]#

Note that a lockfile on this machine names these objects, and pins these snapshots, so that they are kept.

Called whenever a lockfile is written. One note is kept per lockfile and machine, and a later call replaces it. A note of the same path from before notes named their machine is left as it is: it may be another machine’s, and only a person can tell. In this user’s own store (:meth:is_users_own) it can only be this machine’s, and this note takes its place.

Machines are told apart by name only (:func:chartbook.config.get_machine_id): two that share one (a clone that kept its operating system’s identity, with a copied home) write one note per path.

Parameters:

  • lockfile – The path of a chartbook.lock.

  • hashes – The content hashes it names.

  • snapshots – The snapshots it pins, each (commit, made_at).

  • machine – The name to note it under: this machine’s by default; "" for the path alone, as notes were named before they named machines (a CI runner with no name of its own), which no note under a name then takes the place of.

  • labelled – The model versions it pins by label, each (commit, made_at, name, content_hash) (:attr:Root.labelled).

Raises:

ValueError – If one of hashes is not a content hash.

put(path: Union[str, pathlib.Path], links: Iterable[str] = LINKS) → chartbook.store.StoredObject[source]#

Store what a declared path names as an object no pipeline owns, and return its hash.

What a snapshot holds is put by :meth:begin instead, into the pipeline’s folder. An object put here is in pipelines/+unowned/<hex>/, its files under their own names, until store gc finds nothing names it.

path is a file, a directory, or a glob, as in a manifest. It is left exactly where it is. The object is made beside it, by the first of links that the disk allows, and then hashed, so the name an object gets is the hash of what the store actually holds.

Storing the same content twice makes one object. Storing a file whose bytes are already there under another name adds the name.

Parameters:

  • path – An absolute path, which may contain glob characters.

  • links – The kinds of link to try, in order; see :data:LINKS. Pass ("reflink", "copy") for an object that must not change when the original does. If the store already holds this content as a link to a file outside it, the object is then replaced by one that is the store’s own.

Returns:

The stored object.

Raises:

  • FileNotFoundError – If nothing is at path.

  • StoreError – If no kind of link works, or the store’s layout is one this version does not know.

  • ValueError – If links names an unknown kind.

Why a path cannot be written or read on this machine, in a sentence; None when it can.

Windows refuses a path of :data:WINDOWS_PATH_LIMIT characters or more, and a folder of :data:WINDOWS_FOLDER_LIMIT or more, unless long paths are turned on, and says only “No such file or directory” (#136). A path in the \\?\ form has no limit.

chartbook.store.unsynced_part(path: pathlib.Path, size_bytes: int, files: Optional[dict] = None, every: bool = False, content_hash: str = '') → Optional[tuple[str, bool]][source]#

What of an object’s folder is not as its record gives it, in a few words; None when nothing is.

files are the files a reader opens, by their path in the object, each with its size, as the record gives them: the one file of an asset that is a file, under its own name (the object may hold the same bytes under other names too, which are other pins’ business), or each file of a directory, which are then every file of it. Without them, as for a glob, the files the object holds are summed, as they were hashed; so they are when the one file named is not in it and what it holds is not those bytes under other names (by size, and for that rare case by the hash of one, against content_hash), as a directory pinned before records listed its files, which a reader reads as the folder.

A file that is a link is no sync’s doing, and is not judged here:

Meth:

Store.verify and a reader’s own checks see to it. Only sizes and names are looked at, but in that rare case.

Returns:

What is wrong, and whether a sync that has not finished would explain it (False for a file the record does not list, a sync service’s copy most likely, which waiting does not mend).
