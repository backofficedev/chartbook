chartbook.lock#

The lockfile: chartbook.lock, the exact bytes a pipeline depends on.

A pipeline declares which pipelines it reads from in [dependencies]. Pinning freezes what it reads: the content hash of every asset each of those pipelines declares is written to chartbook.lock beside the manifest, and the bytes are in the store (:mod:chartbook.store). The lockfile is source. Commit it: a change to what a project depends on then shows up in a diff, and someone who clones the project can see exactly which data it was built against.

Where the bytes come from. Never from another pipeline’s working directory, which may be in any state. A path dependency is pinned from a snapshot: what its owner declared ready, at a commit (:mod:chartbook.snapshot). A git dependency is pinned from ChartBook’s own clean copy of a commit. The lockfile records the commit either way.

::

from chartbook import lock

report = lock.pin("path/to/pipeline")       # pin what has no pin yet
report = lock.update("path/to/pipeline")    # move every pin forward

pin never moves a pin that exists. It pins a dependency that has no pin yet. update is the one thing that moves a pin: to the dependency’s newest snapshot, or to what its rev means now.

The file is JSON in the index’s own format: the same envelope, and records with the same field names (docs_src/design/index-schema.md). It holds this pipeline’s Pipeline record, cut down to its dependencies, and one record for each asset of each dependency, cut down to its id, its declared path and its content_hash. There is no timestamp, no ChartBook version and no absolute path in it, so pinning twice with nothing changed writes the same bytes.

An asset the other pipeline declares and has not built is recorded without a content_hash. It is not pinned, and asking for it will fail.

A dependency that is a git repository is fetched first (:mod:chartbook.gitcache) and pinned from its checkout. The lockfile records the commit, pin stays at it, and update asks the repository what the rev means now. Such a dependency has only what its repository commits, so data it builds and git-ignores is “not built” here.

A pin is stored as a copy-on-write clone, or as a copy where the disk has no clones (:data:PIN_LINKS), and never as a link to the other pipeline’s own file, so it cannot change when that file is rewritten.

A reference to another pipeline’s asset, data.path("rates:treasury"), resolves through the lockfile to the pinned copy (:func:chartbook.resolve.resolve). The design is “Pinning and isolation” in docs_src/design/asset-graph.md.

chartbook.lock.choose_for_rev(entry: dict, root: str, was: Optional[dict], may_move: bool, snapshots: Callable[[], list], host: str, git_cache: chartbook.gitcache.GitCache, project_dir: pathlib.Path, *, pinned: bool) → tuple[source]#

For a dependency named by its ID with a rev: what to pin it from.

"acme/rates" = { rev = "main" } takes the newest snapshot at or before the commit main is in its repository, which only the repository can say: the one the entry names with repository, or <default_host>/<id>. Its history is walked back from that commit to the nearest one the store has a snapshot of, from that repository (by its first commit); with none, it is pinned from the clone at that commit, and chartbook run builds it, as a git dependency is. A plain pin keeps what is pinned. Pin and run’s plan both ask this.

Returns:

("entry", entry) to pin it by the entry given (a store entry to keep, or a git one); ("snapshot", (snapshot, identity)) to pin it from that snapshot; or ("none", why).

chartbook.lock.clone_instead(entry: dict, root: str, was: Optional[dict], may_move: bool, snapshots: Callable[[], list], host: str, built_here: Iterable[str] = (), *, pinned: bool) → dict[source]#

The entry to pin a dependency by: for one named by its ID that is to be got from its repository, a git one.

Decision 1a: a pipeline named by its ID is read from its snapshots in the store, and its repository is wanted only when the store has no snapshot of it at all. Then, with a default host set ([resolve] default_host), it is cloned from <host>/<id>, or from the repository its entry names, at the commit its entry names if it names one, and pinned and built as a git dependency is.

A pin keeps where a dependency was pinned from: one pinned from the store stays there, and one pinned from its repository stays there, even when the store has a snapshot of it now. An update, or a first pin, looks again. A bare ID, the pipeline itself, and a pipeline built here (built_here, a catalog’s own, by ID) are never cloned.

Parameters:

  • was – Its entry in the lockfile, if it has one.

  • snapshots – The store’s readable snapshots, read when asked for.

  • pinned – Whether the lockfile holds bytes of it (a content hash). An entry with nothing pinned, as a failed first read or a failed clone leaves, is looked at afresh, as a first pin is.

Make the store’s note of a lockfile on this machine name what it pins now, as a pin does.

A machine that only reads (--frozen, a read through the lockfile) is kept this way: store gc on another machine keeps what a note records, and would otherwise know nothing of this one’s pins. The note is replaced with what the lockfile pins now, as pin and update replace it, so a reader’s note follows its pulls; nothing is written when it says that already.

Under CI with no CHARTBOOK_MACHINE_ID, the note names the path alone (:func:_noted_as), as a pin’s does.

chartbook.lock.pin(project_dir: Union[str, pathlib.Path] = '.', store: Optional[chartbook.store.Store] = None, git_cache: Optional[chartbook.gitcache.GitCache] = None, only: Optional[Iterable[str]] = None, clone_missing: bool = True, built_here: Iterable[str] = (), before_writing: Optional[Callable[[chartbook.lock.Lock], Optional[str]]] = None) → chartbook.lock.PinReport[source]#

Pin whatever a pipeline depends on that has no pin yet.

A pin that already exists is left exactly where it is, whatever the other pipeline has done since: :func:update is what moves one.

A path dependency is pinned from its newest snapshot: what its owner declared ready, at a commit (:mod:chartbook.snapshot). None of its data in its folder is read: its manifest and lockfile are, to see that the pin makes no cycle. One that has no snapshot cannot be pinned, and the report says what its owner has to do.

A git dependency is fetched into the git cache and pinned from the checkout, at the commit the lockfile names if it names one. It has only what its repository commits, until chartbook run builds it; the rest of what it declares is not built.

An asset that is declared and not built is recorded as not pinned; the rest of the dependency is pinned all the same.

Parameters:

  • project_dir – The pipeline’s directory.

  • store – The store to pin into; this user’s by default.

  • git_cache – Where git dependencies are fetched to; this user’s by default.

  • only – The keys of the dependencies to pin; the rest keep what the lockfile has, and nothing of them is fetched. All by default. Where there is no lockfile yet, one is made only if something of them is recorded: the first read of a pipeline with no snapshot writes nothing.

  • clone_missing – Whether a dependency named by its ID that the store has no snapshot of is cloned from the default host, and pinned from the clone (:func:clone_instead).

  • built_here – The IDs of pipelines a run builds itself (a catalog’s own), which are never cloned.

  • before_writing – Called with the lockfile as it would be written; what it returns, if anything, is why nothing is written. It takes the place of the default guard, which refuses a lockfile that would make the pipeline’s dependencies cyclic (chartbook run gives its own, which walks the run’s other pipelines too). The report’s refused says why.

Returns:

What was done.

Raises:

chartbook.lock.plan_gc(store: Optional[chartbook.store.Store] = None, forget_missing: bool = False, recent_seconds: float = RECENT_SECONDS, keep_days: float = snapshot.KEEP_DAYS, keep_lineage: bool = False, aggressive: bool = False) → chartbook.lock.GcPlan[source]#

Work out what a store can let go of. Nothing is removed.

First the snapshots: one is kept if a lockfile pins it, if a lockfile pins a model version by its label and it is the newest holding that version (a label resolves to a version an older snapshot may hold, which the pinned moment alone would not keep), if it is the newest of its pipeline, if a label points at a model version in it, or if it was made in the last keep_days days; and with keep_lineage, if a snapshot kept for any of these was made from it (or from a label pointing into it), as far up as that goes (:func:chartbook.snapshot.plan_removals). Then the objects: one is kept if a lockfile the store knows of names it, or a kept snapshot does. The store knows of every lockfile that was pinned or updated into it, and a note only ever adds to what is kept. What a note recorded at its lockfile’s last pin is kept (its objects, and the snapshots it pins; for a note from before notes recorded snapshots, the newest snapshot holding each of its objects), and a lockfile on this machine is read as it is now as well, which adds what it pins after a pull or a switch of branch; one that cannot be found (a deleted project, a drive that is not plugged in) keeps what it named when it was last pinned, unless forget_missing is set. A note of a lockfile on another machine, which a store in a shared or synced folder has, keeps what it recorded and is never forgotten from here; so is a note from before notes named their machine, which may be another machine’s, and a sync service’s copy of a note. A lockfile here at the path of an old note, or of a copy of this machine’s own, is read as well; another machine’s path is never opened (it may be a mount of another host). In this user’s own store, under ~/.chartbook, an old note can only be this machine’s: its lockfile is read alone, as before notes named their machine, and the note is removed once this machine has a note of the lockfile and the lockfile is read (until then, what it recorded is kept), or, with forget_missing, once the lockfile is gone.

Parameters:

  • store – The store; this user’s by default.

  • forget_missing – If True, a lockfile on this machine that cannot be found keeps nothing, and is forgotten when the plan is carried out. Another machine’s lockfiles are never forgotten from here.

  • recent_seconds – An unnamed object newer than this is left alone.

  • keep_days – How long an unpinned snapshot that is not the newest of its pipeline is kept.

Returns:

The plan, for :func:run_gc.

Raises:

  • StoreError – If the store’s notes cannot be read.

  • LockError – If a lockfile that is there cannot be read. Nothing is removed from a store when what it must keep is in doubt.

chartbook.lock.store_has_for(entry: dict, snapshots: Callable[[], list], first_commit: Optional[str] = None, from_repository: bool = False) → bool[source]#

Whether the store has a snapshot a pin of a dependency named by its ID could take, so its repository is not wanted.

Of the ID, at the entry’s commit if it names one; from the repository the entry names, if it names one; and, for one pinned from its repository before, from that repository (first_commit), so that another that gives itself the same ID is no reason not to go back to it. One pinned from its repository whose first commit is not known (from_repository with no first_commit) has nothing in the store known to be its own. Two repositories’ snapshots of the ID with nothing to choose between them are something: pin says which to name, rather than clone. A snapshot dated after now is not one a pin takes.

chartbook.lock.verify(project_dir: Union[str, pathlib.Path] = '.', store: Optional[chartbook.store.Store] = None, note: bool = False) → chartbook.lock.FrozenReport[source]#

Say whether a pipeline can be built from its lockfile alone.

This is --frozen: what CI runs, and what anyone with a store they may only read runs. It opens no repository, fetches nothing, pins nothing and does not write the lockfile. It reads the manifest’s [dependencies], the lockfile and the store, and reports a problem for

  • a lockfile that is not there while the manifest has dependencies;

  • a dependency in the manifest and not in the lockfile, or in the lockfile and no longer in the manifest, or pinned from one place while the manifest now says another;

  • a dependency with nothing pinned;

  • an asset that was declared and not built when it was pinned;

  • a pinned asset that the store does not have.

The stricter choice the design kept for --frozen: where pin records an unbuilt asset and goes on, verify counts it a problem, since the build that follows may need it.

Parameters:

  • project_dir – The pipeline’s directory.

  • store – The store the pins should be in; this user’s by default.

  • note – Whether to make the store’s note of the lockfile on this machine name what it pins (:func:note_this_machine), so that store gc on another machine keeps it: the one thing --frozen writes, and only when the note lacks something. Nothing is written without it.

Returns:

What was found. No problems means the build can go ahead.

Raises:

  • LockError – If project_dir is not a pipeline, or its lockfile is there and cannot be read.

  • ValueError – If its [dependencies] table is malformed.

chartbook.lock.would_pin(project_dir: Union[str, pathlib.Path] = '.', store: Optional[chartbook.store.Store] = None, git_cache: Optional[chartbook.gitcache.GitCache] = None, built_here: Iterable[str] = ()) → Optional[chartbook.lock.Lock][source]#

The lockfile as :func:pin would write it now, worked out and not written; None if it would pin nothing new.

Only the dependencies with no pin yet are worked out: one that has a pin keeps it, as pin keeps it. Nothing is written: not the lockfile, not the store’s note of it, and no object. What a pin would put in the store is not even read, so its records carry no hash: the lockfile says where each dependency would be pinned from, which is what chartbook run walks to find a cycle a pin would close before anything is pinned or built. A git dependency may be fetched into the git cache, and one named by its ID cloned there, as pin would.

Raises:

  • LockError – If project_dir is not a pipeline, or its lockfile cannot be read.

  • ValueError – If its [dependencies] table is malformed.
