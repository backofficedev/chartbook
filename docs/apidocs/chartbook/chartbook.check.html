chartbook.check#

The CI gate: metadata and path checks over a loaded manifest.

chartbook check runs everything here and exits nonzero when any problem is found. It looks at metadata and paths only — required fields under the active policy, the files a manifest points at, the pipelines it depends on, and license expiration dates. It never opens a data file; data-quality checks (row counts, null rates, schema assertions) are a separate concern.

The checks are thin wrappers over machinery the build already uses:

func:

chartbook.conf_validation.validate_source_files for paths and

func:

chartbook.diagnostics.build_diagnostics for required fields.

chartbook.check.check_build_tool(manifest: dict, base_dir: pathlib.Path) → list[chartbook.check.Problem][source]#

A build tool’s task that says chartbook build, as one written before 0.2.0 did to render the site.

With a build command declared ([scripts] build), chartbook build runs that command first, which is the same build tool: the build would run inside itself, and chartbook build refuses. That is a problem, on the build field. Without one, chartbook build there only renders the site, as it did; a warning says that chartbook docs generate is the command that renders (:func:chartbook.run.build_tool_runs_chartbook_build).

chartbook.check.check_dependencies(manifest: dict, base_dir: pathlib.Path) → list[chartbook.check.Problem][source]#

Report every declared dependency that cannot be found.

A path dependency must be a directory with a pipeline’s chartbook.toml in it, and not the pipeline’s own. Nothing in it is built, read or copied. A git dependency is looked at where chartbook pin has fetched it, at the commit the lockfile names. A check never uses the network, so one that has not been fetched draws a warning that says so, not a problem.

In a catalog, a dependency whose key is one of the catalog’s own pipelines must be that pipeline. One ID that means two directories in one build is reported, naming both.

A dependency named by its ID, or a path dependency that is there, with no pin in chartbook.lock draws a warning too: it is not pinned yet, and chartbook pin (or chartbook run) pins its newest snapshot, as the first read of it does. That is a warning and not a problem because a fresh clone is in that state on purpose, and --frozen is the gate that fails on it.

chartbook.check.check_dependency_cycles(manifest: dict, base_dir: pathlib.Path) → list[chartbook.check.Problem][source]#

Report a pipeline that depends, through what it depends on, on itself.

Dependencies between pipelines must form a directed acyclic graph: chartbook run, chartbook build and chartbook snapshot refuse a cycle, and this says so without building. The graph is walked as

Func:

chartbook.lineage.cycle walks it: through the folders on this machine, and through the pins in the store when the store is a folder on this disk. A check uses no network, so a store at a URL is not read, and a cycle that only its snapshots would show is not seen here. The problem is addressed to the pipeline’s own dependency that is in the cycle, or that leads to one among the pipelines it depends on. A pipeline that depends on itself directly, by its own folder or its own ID, is reported by :func:check_dependencies, not here.

chartbook.check.check_ids(manifest: dict, base_dir: pathlib.Path) → list[chartbook.check.Problem][source]#

Warn where a pipeline is named by an ID its folder no longer gives itself, or will be named by another repository’s.

A pipeline’s ID can change: it gets a git remote, and so a scope; it is given [project] id. Its snapshots are then made under the new ID, while a catalog entry keyed by the old one shows only the old ID’s snapshots, and a dependency named by the old one stays at the last of them. Each is a warning, naming the key to write: the old snapshots are still there, and nothing fails.

A catalog’s entry is compared with what its folder calls itself now. A dependency named by its ID (with no commit, which keeps it where it is) is compared with the folders of it on this machine: the catalog’s own, under that ID, and the folders a store on this disk notes its newest snapshots were made in, each one only if it is in the repository those snapshots record. If any of them still calls itself by the dependency’s ID, nothing is said.

A pipeline whose repo_url names another repository than its git remote is named after repo_url’s: a project copied into a new repository with its manifest would claim the original’s ID.

chartbook.check.check_model_labels(manifest: dict, base_dir: pathlib.Path) → list[chartbook.check.Problem][source]#

Look at each model’s labels: does each point at a version that is here?

A label points at a version by the start of its content hash, and a version is made by a snapshot, which is kept in the store of the machine that made it. So a label can be right and its version not be on this machine. That is a warning, as a git dependency that has not been fetched is: nothing can be said, and that is said.

A label that matches more than one version is a problem: it does not say which.

chartbook.check.check_model_lineage(manifest: dict, base_dir: pathlib.Path) → list[chartbook.check.Problem][source]#

Report training data that names a dataframe which is known not to exist.

A model may be trained on another pipeline’s dataframe. That pipeline is looked for where anything else would look for it: in the [dependencies] of the pipeline that declares the model, then among the pipelines being checked with it. Where its chartbook.toml can be read, a dataframe it does not declare is a mistake. Where the pipeline is nowhere to be seen, or is in a git repository that has not been fetched, nothing can be said, and nothing is. Once chartbook pin has fetched it, it is checked like any other.

chartbook.check.check_model_metrics(manifest: dict, base_dir: pathlib.Path) → list[chartbook.check.Problem][source]#

Report every model metrics file that is there and is not well formed.

A metrics file is one flat JSON object of scores. A missing file is

Func:

check_paths’s business, not this function’s.

chartbook.check.check_model_staleness(manifest: dict, base_dir: pathlib.Path) → list[chartbook.check.Problem][source]#

Warn about a model trained on inputs that have since moved.

The model file’s bytes are a version; the snapshot that first held them recorded what each trained_on input was then. An input that is something else now, a local dataframe rebuilt or another pipeline’s pinned elsewhere by chartbook update, makes the model out of date. That is a warning and not a problem: a model may be kept on purpose, and retraining is the pipeline’s build to run.

chartbook.check.check_paths(manifest: dict, base_dir: pathlib.Path, skip_outputs: bool = False) → list[chartbook.check.Problem][source]#

Report every declared file that does not exist on disk.

Parameters:

skip_outputs – If True, do not report missing data files, charts or notebooks. These are what a pipeline builds, so a checkout that has not run it has none of them. Files kept in the repository are still checked: write-ups, notes, the README, the logo and favicon.

chartbook.check.check_required_fields(manifest: dict, base_dir: pathlib.Path, policy_label: str = 'the active policy', warn_only: bool = False) → list[chartbook.check.Problem][source]#

Report every field the active policy requires that is missing or empty.

The policy is the manifest’s resolved policy (catalogs), or the default required-field lists (standalone pipelines); see

Func:

chartbook.diagnostics.get_active_policy. A catalog’s policy.mode is not consulted: it decides what a build does with missing metadata, whereas a check always reports it.

Parameters:

  • policy_label – How to name the policy in messages, so a reader of a CI log knows who required the field.

  • warn_only – If True, no policy was given and the lists are the default recommended ones: each missing field is a warning, not a problem. A missing write-up stays a problem: the format itself requires one for each dataframe and chart, whatever the policy.

A missing build script is said to belong in [scripts] build (:data:PROJECT_FIELDS_WRITTEN_IN), where a manifest writes it now.

chartbook.check.check_sources(manifest: dict, base_dir: pathlib.Path, skip_outputs: bool = False) → list[chartbook.check.Problem][source]#

Report a source that is not there: a DuckDB file that does not exist.

A source’s file is something the pipeline builds, so with skip_outputs it is not reported. Whether the engine connects is not checked, as the data-access design says: a source has to resolve, and whether a table or query in it runs is found out when it is read.

chartbook.check.load_policy(path: Union[str, pathlib.Path]) → dict[source]#

Read the resolved [policy] of a catalog’s chartbook.toml.

Only the policy table is read — the catalog’s member pipelines are not loaded and need not exist on this machine, so a pipeline’s own CI can check itself against the policy of a catalog it is published to.

Parameters:

path – A catalog chartbook.toml or the directory holding one.

Returns:

Dict with mode and per-object-type required field lists.

Raises:

  • FileNotFoundError – If there is no such file.

  • ValueError – If the file is not valid TOML or its policy is invalid.

chartbook.check.not_built_hint(manifest: dict) → str[source]#

What to run when :func:check_paths found a lone pipeline that has built nothing yet.

chartbook build is named only when there is a build script for it to run, as chartbook docs generate names it.

chartbook.check.run_checks(manifest: dict, base_dir: Union[str, pathlib.Path], within_days: int = DEFAULT_WITHIN_DAYS, today: Optional[datetime.date] = None, policy_label: str = 'the active policy', skip_outputs: bool = False, policy_given: bool = True) → list[chartbook.check.Problem][source]#

Run every check over a loaded manifest.

Parameters:

  • manifest – A manifest from :func:chartbook.manifest.load_manifest (pipeline or catalog).

  • base_dir – The directory holding that manifest’s chartbook.toml.

  • within_days – The license-expiration window, in days.

  • today – The date to measure license expiration from.

  • policy_label – How to name the policy in required-field messages.

  • skip_outputs – If True, built files (data, charts, notebooks) need not exist; see :func:check_paths.

  • policy_given –

    False when no [policy] was given anywhere: the default recommended fields are then warned about, not problems; see

    func:

    check_required_fields.

Returns:

Every problem found, sorted by file then table; empty for a healthy project.
