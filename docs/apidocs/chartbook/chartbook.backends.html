chartbook.backends#

Backends: the engines behind a pipeline’s [sources].

A dataframe is a file, or it is a table or a query in a source: a named, configured instance of a backend, declared in the manifest::

[sources.local]
backend = "duckdb"
url = "duckdb:///./_data/local.duckdb"

[dataframes.slopes]
source = "local"
query = "select Date, SVENY10 - SVENY02 as slope from fed_yield_curve"

The rule, from docs_src/design/data-access.md: a name resolves to a location; the backend runs the query; Arrow comes back; Polars wraps it. ChartBook never parses, plans or rewrites SQL. It knows where a name lives and which dialect lives there, and it substitutes identifiers. The SQL is the user’s (:func:chartbook.data.sql).

Three backends are built. parquet is what a file-backed dataframe has always been: it reads the file, and in SQL it is read_parquet('…'). duckdb is the local engine: a file, or :memory:, that holds tables and runs any SQL that mentions them, and reads parquet files too, so a query can join a table of one source with a file of this pipeline. databricks is a SQL warehouse (:mod:chartbook.backends.databricks), whose driver pip install chartbook[databricks] installs. A source’s backend is found by its name: duckdb here, any other in the entry-point group chartbook.backends, as a kind of store is in chartbook.stores. What a backend does for ChartBook is :class:Backend. A manifest that names a backend nothing provides is refused, so that the message can say so.

Credentials never enter a manifest. A source’s url is the public part. The machine supplies the rest (:func:source_url): an environment variable CHARTBOOK_SOURCE_<NAME>_URL holding a complete URL, then a url for the source in ~/.chartbook/sources.toml, then the manifest’s URL alone, which is all a DuckDB file needs. A manifest URL that carries a user name or a password is refused when the manifest loads, and so is a machine URL for a different engine than the manifest’s backend. A warehouse’s backend may take its credentials from the engine’s own environment variables too, and sends them only to a host the machine names.

No writes. A connection to a DuckDB file is opened read-only. ChartBook never creates, loads or alters a table; table and query describe what the pipeline’s own tools have already made. A :memory: source is the exception by nature: it holds nothing until something is put in it through :func:chartbook.data.connect, so it is one writable connection for the life of the process.

Connections are not kept. A DuckDB file is opened afresh for each load, so a rebuilt file is seen on the next call. A lazy frame handed out keeps its own connection alive for as long as it lives, and DuckDB locks the file against writers for that long; drop the frame before rebuilding the file in the same process.

class chartbook.backends.Backend(url: str, source: Optional[str] = None)[source]#

An engine behind a source: what ChartBook asks of one.

name is what [sources.x] backend says. A backend is made from a source’s public URL, as its location carries it, and the source’s name, by which the machine’s own URL and credentials are found; it connects only when asked. Every call that reaches the engine raises

Class:

BackendError with the engine’s own message when it fails; an error found only when a lazy frame is collected comes as Polars’ ComputeError with the engine’s message in it, or as the

Class:

reads_files says whether SQL run in it may name a file of this machine as :class:ParquetBackend writes one, read_parquet('…'): so whether :func:chartbook.data.sql may join this engine’s tables with a pipeline’s files in one query.

A DuckDB file, opened read-only for each use, or an in-memory engine.

A file is opened afresh by every :meth:connect, so nothing in the process keeps a stale handle: a frame handed out keeps its own connection for as long as it lives, and no longer. The in-memory engine of a :memory: source is one connection for the life of the process, since what is put in it through data.connect() is all it holds.

chartbook.backends.duckdb_path(url: str, manifest_dir: Union[str, pathlib.Path]) → str[source]#

The file a duckdb:// URL names, absolute; or :memory:.

Follows the SQLAlchemy convention: duckdb:///relative.db is relative to the pipeline’s directory, duckdb:////abs/path.db is absolute, and duckdb:///:memory: is nothing on disk.

Raises:

ValueError – If the URL has a host or a user (duckdb://x/f), connection options (?access_mode=…) or a fragment. ChartBook passes none of those to the engine, so it refuses to look as if it did.

chartbook.backends.subselect(sql: str) → str[source]#

A query as a table expression: (…) on its own lines.

Two things are dropped from the end of the text, each as many times as one is left there, so that a query that ends with ;, with a -- comment, or with both (select … from t; -- note) still stands where a table would: a semicolon that is the last character; and a -- comment that runs to the end, when its -- is outside every string ('…', E'…', $$…$$), quoted identifier ("…", `…`) and block comment, as :func:_ends_in reads them. Nothing else changes: a ; or a -- inside quotes stays, and a comment after a quote the scanner takes as left open stays too, which the engine reads as the comment it is. The parenthesis closes on a new line.
