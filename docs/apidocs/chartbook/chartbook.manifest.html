chartbook.manifest#

Load and process chartbook.toml manifests (format v2).

A v2 manifest has a single [project] metadata table plus the entity sections [charts], [dataframes], [notebooks], [notes] and [models], a [dependencies] table naming the pipelines it reads from and a [scripts] table of named commands (pipelines), or a [pipelines] registry and optional [policy] (catalogs). Every [project] field is optional; defaults are filled at load time. See docs_src/design/toml-format-v2.md for the full specification.

v1 manifests (the old [config]/[site]/[pipeline] layout) are not supported; loading one raises an error pointing at the migration script.

Replace each pipeline’s modification-time stamp with its code-change time.

Loading a manifest records source_last_modified_date from file modification times, which is cheap and is all most callers need. Building pages calls this first, so that what a page shows comes from

Func:

find_latest_code_change.

Parameters:

  • manifest – A loaded manifest, pipeline or catalog. Updated in place.

  • known – Times already worked out, by pipeline ID, to use as they are. An incremental build passes the ones it recorded for pipelines it is not regenerating, which spares git a call for each.

Returns:

The time now set for every pipeline, by pipeline ID.

chartbook.manifest.catalog_entry_dir(base_dir: Union[str, pathlib.Path], path: pathlib.Path, where: str = '') → pathlib.Path[source]#

The folder a catalog’s entry names, by its path relative to the catalog’s folder.

The path is joined to the catalog’s folder with every link in that folder’s own path followed, as chartbook catalog add works it out. One written from the folder as it is named instead (by hand, or by an older catalog add, with a home folder reached through a link), or read where .. is taken before a link is followed (realpath on Windows, through a junction), is joined as written when the first way finds no chartbook.toml and this one does. That works only where the catalog is reached as it was named when the path was written, so it is said, with the path to write instead.

Parameters:

  • base_dir – The catalog’s folder, as it was named: the commands that read a catalog keep the links in the path they were given.

  • path – The entry’s path, for this platform (:func:resolve_platform_path).

  • where – The entry, to say it when its path is read the second way (chartbook.toml: [pipelines."acme/rates"]); nothing is said without it.

Returns:

The folder, resolved.

chartbook.manifest.catalog_member_dirs(base_dir) → dict[source]#

The folder of each pipeline of a catalog that is on this machine, by its ID, from the catalog’s manifest alone.

What a build of the catalog would read from this machine, before it reads any of it: no member’s manifest is loaded, and nothing of a member runs. A pipeline the catalog shows from the store (an entry with no path) has no folder here and is not listed. An explicit entry’s folder is listed as the entry names it, whether or not a chartbook.toml is there yet: the caller says what to do about one that is not.

Parameters:

base_dir – The catalog’s folder.

Raises:

  • FileNotFoundError – If there is no chartbook.toml there.

  • ValueError – If the manifest is not a catalog’s, or cannot be read.

chartbook.manifest.find_latest_code_change(base_dir: Union[str, pathlib.Path]) → datetime.datetime[source]#

Find when a pipeline’s source last changed, asking git where it can.

File modification times say when a file last landed on this disk. A fresh clone stamps every file with the moment of the checkout, so on a build server they report code that is a year old as changed just now.

When the pipeline’s source is committed and unmodified, the answer is the time of the last commit that touched it. With uncommitted changes, or outside a git repository, it is the newest modification time, as

Func:

find_latest_source_modification gives.

Parameters:

base_dir (Union[str, Path]) – The base directory of the pipeline.

Returns:

The time of the last change, in local time.

Return type:

datetime

chartbook.manifest.read_scripts(raw_manifest: dict) → dict[source]#

Read a pipeline’s named scripts: [scripts], and [project] build.

A script is one string, run by a shell in the pipeline’s directory::

[scripts]
build = "doit"
test = "pytest"
fetch = '''
module load python/3.12
python src/pull_wrds.py
'''

A value of several lines is one script, so what one line sets up the next can use. [project] build is the same thing as [scripts] build and is still read; a manifest gives it in one place.

Scripts are not tasks. There is no order among them and none depends on another. See “Running things” in docs_src/design/asset-graph.md.

Parameters:

raw_manifest – The dict parsed from chartbook.toml.

Returns:

The scripts by name. build is in it if either table gives one.

Raises:

ValueError – If the table is malformed, a name could not be typed on a command line, a script is empty, or build is given twice and differently.

chartbook.manifest.require_chartbook(raw_manifest: dict, source: str = 'chartbook.toml') → None[source]#

Stop when the ChartBook running is not one the project asks for in [project] requires_chartbook.

The value is a version specifier, as a pip requirement has it after the package’s name (">=0.2.0", ">=0.3,<0.5"), compared with this package’s version. Every command that acts on a manifest reads the project’s type first (:func:resolve_project_type calls this first), so an older ChartBook stops here, with the command that installs one that meets it, before something newer in the manifest confuses it. A ChartBook from before 0.2.0 does not know the key, and warns that it is unknown; the check holds from 0.2.0 on.

Raises:

  • RequiresChartbookError – If this ChartBook does not meet it.

  • ValueError – If the value is not a specifier.

chartbook.manifest.validate_dependencies(dependencies, base_dir: Union[str, pathlib.Path]) → dict[source]#

Validate a pipeline’s [dependencies] table.

A dependency is another pipeline that this one reads from. The key is the name this pipeline knows it by, which is a pipeline ID; the value says where to get it::

[dependencies]
"ftsfr/rates" = {}
yields = { id = "ftsfr/yield_curve", commit = "3f2a9c1" }
"ftsfr/fed_yield_curve" = { path = "../fed_yield_curve" }
"ftsfr/crsp_compustat" = { git = "https://example.org/ftsfr/crsp_compustat", rev = "a1b2c3d" }

An entry with neither path nor git names the pipeline by its ID alone (the key, or id), and is pinned from its snapshots in the store, with no folder of it and no clone: the newest, or the newest at the commit commit starts; repository keeps to the snapshots made in that repository, when more than one claims the ID. Such an entry gains _store, the pipeline’s ID, and _repository.

Identity and location are kept apart on purpose. Code, lineage and the index say ftsfr/fed_yield_curve; only this table says where that is, so moving a repository changes one line. See “Identity and location” in docs_src/design/asset-graph.md.

Only the table’s shape is checked. Whether a path holds a pipeline is chartbook check’s business: a manifest has to load on a machine where a dependency is not there yet.

Each path entry gains _resolved_path, the directory made absolute.

Parameters:

  • dependencies – The raw [dependencies] table.

  • base_dir – The pipeline’s root directory, which a path is relative to.

Returns:

The entries by key.

Raises:

  • UnsupportedRevisionError – If a key carries @rev.

  • UnsupportedRegistryError – If a key carries a registry prefix.

  • ValueError – If the table or an entry is malformed.

chartbook.manifest.validate_models(manifest: dict, base_dir: pathlib.Path) → dict[source]#

Validate a pipeline’s [models.<id>] tables.

A model is a file, or a directory of files, that the pipeline produces: path says where. trained_on lists the dataframes it was trained on, as references; metrics_path names a JSON file of scores; and docs_path or docs is its write-up. See docs_src/design/models.md.

A dataframe in trained_on may belong to this pipeline ("treasury_rates") or to another ("ftsfr/rates:treasury_rates"). One of this pipeline’s must be declared here. Another pipeline’s must be in a pipeline that [dependencies] declares. Whether that pipeline has such a dataframe is for chartbook check to say.

Each entry gains _resolved_path and _trained_on, the parsed references to the dataframes it was trained on.

Parameters:

  • manifest – The pipeline’s manifest, with dataframes and dependencies loaded.

  • base_dir – The pipeline’s root directory.

Returns:

The model tables by key; empty if the pipeline declares none.

Raises:

ValueError – If a table is malformed, a key is not a legal name, or trained_on names something that is not a dataframe, a dataframe of this pipeline that it does not declare, or a pipeline that [dependencies] does not declare.

chartbook.manifest.validate_series(dataframe_manifest: dict, dataframe_id: str) → dict[source]#

Validate a dataframe’s [dataframes.<id>.series.<key>] tables.

A series is one column of a dataframe, given an address (dataframe#key) so that a name, units, a frequency and a write-up can be attached to it. Declaring one is how a column is documented, not how it comes to exist: every column is in the index whether or not it has a table here. See “Addressing a series inside a dataframe” in docs_src/design/asset-graph.md.

Each table’s column is filled in with its key when it is not given.

Parameters:

  • dataframe_manifest – The dataframe’s manifest entry.

  • dataframe_id – Its key, for error messages.

Returns:

The series tables by key; empty if the dataframe declares none.

Raises:

ValueError – If the tables are malformed, a key is not a legal name, or two series claim one column.

url = "duckdb:///./_data/local.duckdb"

See docs_src/design/data-access.md. Each source gains _resolved_url: for a DuckDB file, the URL the machine opens it with, from :func:chartbook.backends.source_url, with a relative file made absolute; for another engine, the manifest’s public URL, from which its backend finds the machine’s URL and credentials when it connects, so that no credential is carried around.

Raises:

ValueError – If the table is malformed, a name is not a legal name, a backend is not built, a url carries credentials, or a url does not match its backend.

chartbook.manifest.with_dependency(text: str, key: str, entry: dict) → str[source]#

A manifest’s text with one dependency added to [dependencies], all else as it was.

The file is edited as text, not written again from what it parses to, so its comments, order, spacing and line endings stay. The line goes just under the [dependencies] header; with no such table, one is added at the end. Each place is tried, and an edit is kept only if the result parses to the manifest as it was with that one entry added, so a line that looks like the header inside a string is never written into.

Parameters:

  • text – The chartbook.toml as it is.

  • key – The dependency’s key.

  • entry – Its table, of strings: {}, {"id": ...}, {"commit": ...}.

Raises:

ValueError – If the key is in it already, or no edit gives the manifest with the entry added (the message has the line to add).
