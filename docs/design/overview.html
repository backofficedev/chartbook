Design: start here#

Note

The entry point to the design documents. It is written for someone, or some agent, who has never seen this project and has to continue building it. It says what ChartBook is, the words it uses, what is built, what to build next and in what order, and where every decision is written down.

Last revised 2026-10-12 (Versions, 2026-10-18), after the 0.2.0 prepared that day and never published, the index, declared models, and all five parts of step 3: declared dependencies, the store, pinning, references to another pipeline’s assets, and git dependencies. Step 3 is built. The next step is 4, running and build records.

What ChartBook is#

ChartBook is a Python command-line tool and library. A data project describes what it produces in one file, chartbook.toml, and ChartBook turns that description into a documentation website, a way to load the data by name, and (the work ahead) a record of what depends on what.

Three sentences hold most of the design:

  1. The manifest is the contract. chartbook.toml says what exists and where. ChartBook reads it; it never requires your code to call ChartBook.

  2. ChartBook publishes; it never orchestrates. It does not schedule, retry or run your analysis. Your own tool (doit, make, a shell script) does that.

  3. Everything works for one person on one laptop with no server. Sharing is the same files, in git or on a shared drive.

It is experimental and pre-1.0. Breaking changes are allowed, with a changelog entry that says what to do instead (Stability).

The picture#

organization (scope)        ftsfr
  pipeline                  ftsfr/fed_yield_curve          one repository, one chartbook.toml
    dataframe               …:treasury_rates               a parquet file (later: a table)
      series                …:treasury_rates#dgs10         one column of it
    chart                   …:chart/curve_today            an HTML file
    notebook                …:notebook/analysis
    note                    …:note/methodology             a page of prose
    model                   …:model/rate_forecaster        a trained model

catalog                     many pipelines, browsed and searched as one site

Data is the spine. Organization, pipeline, dataframe, series: that chain is what people load, depend on and cite. Charts, notebooks, notes and models hang off a pipeline and say what kind they are. This was the maintainer’s explicit correction to an earlier draft that treated all assets alike.

Words#

The vocabulary is a page of the documentation, Vocabulary, and that page is the one place the words are defined; the design documents use them in those senses. The sentence to keep in mind, the maintainer’s (2026-10-14): a manifest asks, a lockfile records what was got, a snapshot records what was made, and an index records what a site shows. The chain is repository → index → pages → site, with a writer per site tool and the site tools called by their names.

Rules that settle arguments#

These come from the maintainer and from Design: the asset graph. When a design question is close, they decide it.

  1. Scale to zero. No capability may require a running service to be useful to one person on one machine.

  2. A convenience is never a requirement. data.path() is nice. A script that hardcodes the same path, in any language, must keep working.

  3. No orchestration. No scheduler, retries, backfills, run history or run UI. Export the graph to a tool that has them.

  4. No plugin system before a second implementation exists. Leave one internal seam. Write the second implementation. Then extract the interface.

  5. Some things are singular. Hash computation, name resolution and the index schema each have exactly one implementation, on purpose.

  6. No features for machines alone. Anything built for programs must fall out of something that already helps a person.

  7. Refuse, do not guess. Syntax that is reserved for later raises “not yet supported”. It never quietly does something else.

  8. Plain files stay plain. A declared path is the real location of the real file. The store links to it; it never moves it.

The full list of things that will be declined is “Not doing” in the asset graph. Read it before proposing a feature.

Versions#

Decided by the maintainer, 2026-10-12.

  • The asset graph is one change, not a release per step. The steps under “What to build next” do not each get a minor version. Do not bump the version in a pull request.

  • 0.2.0 is the release. The asset graph, the store, the versioned catalog and the review before the release ship together as 0.2.0, the first release since 0.1.1 (decided 2026-10-18; the 0.2.0 prepared on 2026-10-12 was never published). Until it is published, what lands goes under “Unreleased” in the changelog.

  • 1.0 is a long way off, on purpose: there is room for many more changes before any promise of stability. Nothing here should be planned as “the last thing before 1.0”.

What to build next, in order#

Who decided what

The maintainer has decided the destination (everything in Design: the asset graph, Design: the index, Design: models and Design: data access) and that the index comes first. The order of the steps after the first, and their boundaries, are the recommendation of the last person to work on this. Change them if a better cut appears, and say so here.

Each step ends with something a user can run. Do them one at a time, each as its own branch and pull request.

Step 1. The index — built#

chartbook docs also writes one JSON file that describes everything: index.json, beside the HTML. It has Catalog, Pipeline, Dataframe, Series, Chart, Notebook and Note records, each asset with a fully qualified id, a structured ref and a content hash. The code is chartbook/index.py and chartbook/hashing.py; the JSON Schemas are in chartbook/schemas/; the loader reads [dataframes.x.series.y].

Design: the index is the specification, and its last section, “What the first implementation does”, says exactly what is written and what is not. Nine things were settled while building it. The maintainer has decided three; six are listed there as proposed, still to confirm.

Left for later steps, on purpose: Build records, dependencies, Model records, and rendering the site from the index.

Step 2. Declared models — built#

A pipeline can declare a trained model in [models.x], ask for its path (chartbook path model/x, chartbook.models.path("x")), check it, and get a page and a Model record in the index. This is slice M1 of Design: models; its section “What is built” lists every file involved and eight things that were settled while building it, all proposed.

Left for later steps, on purpose: versions and labels (@v3, @champion), parts (model/x#file), and anything that crosses a pipeline boundary.

Step 3. Dependencies, the lockfile and the store#

Goal: data.path("fed_yield_curve:treasury_rates") works, and returns a frozen copy. (Met 2026-10-12, with 3d.)

The case this step is for

A model in one pipeline, trained on data from another, reproducibly. The maintainer was explicit: cross-pipeline training data is what ChartBook is going for, not a later refinement, and it is one reason all of this is being built as one change with no release in between.

Today a model can state that it was trained on another pipeline’s dataframe (Design: models). Nothing fetches that data, pins a version of it, or records which bytes were used. This step makes it real. Judge every design choice in it against that case first, and against “a chart of another pipeline’s data” second.

It is the largest step, and the first where the design has never met code. Build it as five pull requests, in this order. Each leaves main working.

Everything that used to look a pipeline up by name now calls locate_pipeline(): the catalog lookups behind data.load(pipeline=…), the index, the model page and check.

Not done in 3a, on purpose. Nothing is fetched, copied or pinned. pipeline:asset is still refused wherever a path is asked for: it must resolve to a frozen copy, never to the other pipeline’s working directory, so making it resolve early would change what the same text means later. No example pipeline declares a dependency yet; examples/rate_forecast arrives in 3d. Pages do not list a pipeline’s dependencies.

Proposed: implemented in 3a, and waiting on the maintainer’s yes. Each was open or unstated in the design.

  1. A git dependency may be declared now, though nothing fetches it until 3e. It is validated, recorded in the index, and check warns that it was not looked at. (The table above says “path first”. Refusing git until 3e was the other option; the design’s own example manifest would not have loaded.)

  2. rev is optional on a git dependency. With none, the revision is whatever the repository’s default branch has when it is pinned, as a path is whatever the directory holds. What that fetch does is 3e’s to settle.

  3. { rev = "…" } with no git is refused, with a message. Design: chartbook.toml Format v2 shows that form, which needs [resolve] default_host to work out the URL. Not built.

  4. The key of [dependencies] is a plain pipeline ID. No URL, and no @rev: a revision goes in the entry. Design: references said such a key may carry both.

  5. A reference may leave the scope off when exactly one dependency has that name, as a catalog lookup allows. A name that fits two dependencies is an error, and is not passed on to the catalog to be guessed at.

  6. A trained_on that names an undeclared pipeline warns when the manifest loads, so build shows it as well as check, and check does not fail on it. It becomes an error in 3d.

  7. check needs a path dependency to be on disk, with --skip-outputs too. A dependency is not something this pipeline builds. A project whose CI checks out one repository will want git dependencies, which is 3e.

  8. Within one build, a pipeline goes by the build’s name for it. If a pipeline calls ../fed_yield_curve yield_curve and the catalog calls that directory ftsfr/fed_yield_curve, the catalog’s index says ftsfr/fed_yield_curve in both dependencies and inputs. Alone, the pipeline’s index says yield_curve.

  9. One ID for two directories is reported by check on a catalog, when a dependency’s key is a catalog pipeline’s ID and its path is a different directory. Inside one pipeline the case cannot arise (a TOML table has each key once), and two pipelines of a catalog may point one name at different places without it being reported.

  10. A catalog with a [dependencies] table does not load. It reads from no pipeline.

  11. An unknown key in an entry is an error, not a warning, so that a later key (branch, tag) is never silently ignored by an older ChartBook.

  12. The index’s shape for a dependency: see Design: the index, “Decided while building it”, items 10 to 13.

One row of the table above cannot be met as written. “A cross-pipeline trained_on or chart input must name a declared dependency.” A chart has no way to name another pipeline’s dataframe: its dataframe field must be one this pipeline declares, or the manifest does not load. So only trained_on is covered. A chart of another pipeline’s data needs the chart’s inputs field (Design: the index) or a looser dataframe, and a page that can render it; that is best decided with 3d.

3b, as built#

Added 2026-10-12. Nothing a user sees, apart from one command. The store is the piece that pinning sits on, and it is tested alone.

from chartbook.store import FolderStore

store = FolderStore("~/.chartbook/store")
stored = store.put("_data/treasury_rates.parquet")   # the file stays where it is

The tests

Not done in 3b, on purpose. Nothing puts anything in the store: no pin, no lockfile, no gc. builds/, the index from a build’s inputs to its output, is a name the layout keeps free and nothing writes to. The link kinds cannot be chosen in settings.toml; a caller in code can pass its own list.

Proposed: implemented in 3b, and waiting on the maintainer’s yes.

  1. An object is hashed after it is stored, not before. put links or copies the file into the store first and then hashes what the store holds. So an object’s name is right even if the original was being rewritten while it was stored.

  2. A clone or a copy is made read-only in the store. A hard link is not, because it cannot be: see the first correction below.

  3. put takes the kinds of link to try. The default is the designed four. A caller that must have a frozen object passes links=("reflink", "copy"), and what comes back says whether it is frozen (stored.frozen). So 3c can tell a user, when it pins, how many of the pins are links to files that can still change. Nothing chooses for the user.

  4. The same bytes under another file name are one object with both names in it. A file’s hash does not include its name, and a path into the store has to end in the right one.

  5. An empty directory is not stored. There is nothing to pin, and its hash would be the hash of an empty file.

  6. The store says which layout it has, in store.json. A store laid out by a later ChartBook is refused, not misread.

  7. A store comes into being when something is first put in it, never by being looked at. chartbook store verify on a machine with no store says “OK (0 object(s))” and creates nothing.

  8. An object is built in tmp/ and moved into place with one rename, so another process sees all of it or none of it, and two that store the same content at once end with one object.

  9. verify exits 1 if any object has changed, and prints hash: what is wrong. It ignores the same operating-system files that hashing ignores, so Finder looking inside the store does no harm.

  10. A symlink in the store points at the real file, with any links on the way resolved, so the store never holds a link to a link.

Where the design was wrong about what a disk does. Both are in Design: the asset graph, “Links, not copies”, and are marked there.

  1. “Hardlink: make the store side read-only.” A hard link has no store side. Both names are one file with one set of permissions, so making it read-only makes the upstream’s own file read-only, and its next build fails on a file it wrote itself. That would break rule 2, “a pipeline that hardcodes its paths keeps working”. So a hard-linked object is left writable, and verify is what protects it.

  2. “The copy rung will be exercised: a shared network mount is a different filesystem, so neither reflinks nor hardlinks reach it.” A symlink comes before copy in the ladder, and a symlink does reach across filesystems. So with the store on one disk and the data on another, an object is a symlink, never a copy. Copy is reached only where symlinks are not allowed, which in practice is Windows without the privilege.

Answers to the open questions#

The maintainer answered five of these on 2026-10-12, after 3a, a sixth with 3d and the last with 3e. All seven are decided.

  1. Where the store lives. Decided. One store per user, at ~/.chartbook/store/, beside the settings file that is already there. CHARTBOOK_STORE, or [store] url = "…" in settings.toml, points it somewhere else: a bigger disk, or a drive a team shares. Not one store per project, because ten projects that pin the same upstream should hold one copy.

    Layout: one directory per asset, named by its hash, holding the asset’s files under their own names.

    ~/.chartbook/store/
  objects/sha256/7f/3a9c…/treasury_rates.parquet          a one-file asset
  objects/sha256/b2/09e1…/year=2024/part-0.parquet        an asset of many files
  builds/                                                 kept for step 4

    The file names are kept because the path handed to a reader has to still end in .parquet, and a partitioned dataset has to keep folders like year=2024/.

  2. How the store links to a file. Decided: all four kinds, in the designed order. Reflink, then hardlink, then symlink, then copy (Design: the asset graph, “Links, not copies”). The builder of 3a asked to drop the two middle ones, and the maintainer kept them: they are the cheapest on every disk.

    What that means, so that nobody is surprised later. A reflink or a copy is the store’s own bytes: nothing outside the store can change it. A hardlink is the upstream’s file under a second name, and a symlink only points at it. If the upstream pipeline rewrites _data/rates.parquet in place, an object stored either of those ways changes with it, and still sits under its old hash. chartbook store verify is what catches that, by hashing every object again. So the step’s “Done when” line, “editing the upstream’s data does not change what the downstream reads”, holds on a disk with reflinks (APFS, btrfs, XFS) and wherever the upstream replaces its files instead of rewriting them; elsewhere it holds only until the upstream rebuilds, and verify says when it has stopped holding.

    Decided later the same day, with 3d: a pin asks for a reflink, then a copy, and nothing else. The store still offers all four kinds. So the paragraph above now describes what a build cache would get, and a pin is frozen on every disk (“3d, as built”).

  3. The lockfile’s shape. Decided. JSON, in the index’s own format: the same envelope ("schema": "chartbook/lock/v1") and a records list. It holds this pipeline’s Pipeline record with only its id and dependencies (each now with a pinned_hash), and, for each pinned asset, the upstream’s own record for it, cut down to id, ref, pipeline, location.path, content_hash and size_bytes. No timestamp and no absolute path, so pinning twice with nothing changed writes the same bytes and shows no diff. Build records join it in step 4. This is what “no second format” in Design: the index asks for.

  4. pin when an upstream has not been built. Decided. Pin what is there and say what is not. An asset whose file is missing gets a record with no content_hash, exactly as the index writes one today. Asking for its path later fails, and says to build it upstream and run chartbook update. So an upstream with ten dataframes, one of which needs a subscription you do not have, is still usable. The stricter choice, refusing to pin at all, is what --frozen is for in step 4.

  5. Hidden files when hashing a directory. Decided. Skip a short, fixed list of files that operating systems create by themselves: .DS_Store, Thumbs.db, desktop.ini, and any name starting with ._. Every other file counts, hidden or not. A Zarr dataset keeps its real metadata in .zarray and .zattrs, and leaving those out would give two different datasets one hash. No release carries the earlier rule, so this changes it without a new algorithm prefix. It is built with the store (3b), which is keyed by it.

  6. A git dependency. Decided, and built in 3e. Clone once into ~/.chartbook/git/, fetch on update, and check the wanted commit out into a directory beside it. From there it is a path dependency. The lockfile records the full commit hash that rev meant when it was pinned.

    What had to be decided first: a fresh clone has the upstream’s code, not its data, because built data is usually git-ignored. So a git dependency can only be pinned where the upstream commits its outputs. Otherwise it needs step 4 (run the upstream’s build) or a shared store to download from. The maintainer’s answer: build it now, plainly, and have it say so. It does.

  7. data.load("pipeline:asset"). Decided, and built in 3d. data.load("treasury_rates") loads this pipeline’s own dataframe, data.load("fed_yield_curve:treasury_rates") loads the pinned copy, and the two-argument data.load(pipeline=…, dataframe=…) keeps meaning “through a catalog”. The snapshot model#

Decided by the maintainer, 2026-10-13. Two names make it concrete: yield_curve makes data, and rate_forecast uses it.

Why. Pipelines are worked on side by side, by people and, more and more, by agents working in parallel, one to a pipeline. Someone is always half-way through a change in yield_curve. That must not reach rate_forecast. So the store is the one thing every pipeline reads from: it is read-only, and it changes slowly and on purpose.

The rules.

  1. A pipeline never reads, hashes or builds in a folder it depends on. rate_forecast does not look in ../yield_curve/_data/, and nothing it runs is run there.

  2. A snapshot is every asset a pipeline declares, as built at one commit, kept in the store and labelled with that commit. Dataframes, charts, notebooks, notes and models alike.

  3. A snapshot is made on purpose, by the pipeline’s owner, and only when everything is committed. It is not made by every build. That is how a pipeline is declared ready for others, and what keeps the label “built by this commit” true.

  4. pin and update choose among snapshots. They do not copy whatever is in the folder.

  5. Nothing that happens in yield_curve rebuilds rate_forecast. It rebuilds when it asks to move its pins, with chartbook update.

  6. chartbook run builds the pipeline it is run in. A git dependency is the one thing it builds besides, once, in ChartBook’s own clean copy of the commit: nobody works there, so there is nothing to disturb. Data that is pulled from outside is refreshed on purpose, with --force, and not because time has passed.

  7. Taking whatever is in a folder stays possible, as an option that is off by default and out of the way, for someone working on both pipelines at once.

Proposed: implemented in 4a, and waiting on the maintainer’s yes.

  1. [project] build and [scripts] build are one thing. Both are read. A manifest that gives both, with different text, does not load. Pages and the policy keep reading project.build, which the loader fills from whichever was written.

  2. A script’s name matches [A-Za-z0-9._-]+, the rule an ID component already has, because it is typed after chartbook run. An empty script does not load.

  3. A script is handed whole to bash -e -c, to sh where there is no bash, and to cmd on Windows. It runs in the pipeline’s directory, with the environment chartbook run was started in, and its output is not captured. bash because module load and conda activate expect it.

  4. In a catalog, the script is run in each of the catalog’s pipelines, one that another of them depends on first, and otherwise in the order the catalog lists them. A pipeline the catalog does not list is not run, whoever depends on it. Two of its pipelines that depend on each other are an error that shows the loop, and nothing is run.

  5. The pipeline that was asked for must have the script. A pipeline of a catalog that has no script by that name is passed over and named. A name that no pipeline has is an error.

  6. Only build pins, and only build reaches a git dependency. chartbook run test writes no lockfile and fetches nothing.

  7. Each pipeline is pinned just before its own build. A pipeline with no build script is not pinned for.

  8. What cannot be pinned stops the run before that pipeline’s build: a dependency that is not there and has nothing pinned, a repository that cannot be fetched, a lost pin. A dependency that has gone and is pinned is no trouble.

  9. The exit code is the failed script’s. One stopped by a signal gives 128 plus the signal’s number, as a shell reports it. What ChartBook printed is flushed before a script starts, so a log has the lines in order.

  10. A git dependency’s working copy is ~/.chartbook/git/work/<host>/<owner>/<name>/<commit>/: the checkout’s files, made writable. It is made once and kept. It is shared by every project of this user that depends on that commit. The checkout itself is never written to.

  11. “Built” is a file in the working copy, .chartbook-built, written when the build exits 0 and removed before a forced one. A build that fails leaves the copy unbuilt, so the next run tries again. One that is built says built already, at 4f2a91c.

  12. What a built git dependency itself depends on is not looked at again, unless --force is given. It was needed to build it, and it is built.

  13. A git dependency with no build script is not mentioned. That is the ordinary case of a repository that commits its data.

  14. pin and update pin a git dependency from its working copy when there is one, and from the checkout otherwise.

  15. Which commit is built. The lockfile’s, if it names one, since a pin does not move. Otherwise what the rev means now.

  16. The index lists every script under scripts, sorted by name. The schema already allowed it.

  17. A catalog has no [scripts]. A manifest that gives one does not load.

  18. What it says. One line for each pipeline it runs in, with the directory when that is not where the command was given. Pins are mentioned only when something happened, and a lockfile is never written without a line that says so.

  19. An update that moves a git dependency’s commit lets go of what was built at the old one. This changes one case of a rule proposed in 3c (number 7 there: an asset the other pipeline “declares and no longer has on disk keeps its pin”). Example: ref_data is pinned at commit A, with daily_prices built there by run. update moves it to commit B, where nothing is built yet. Under the 3c rule the lockfile would then say commit B beside the bytes built from A. Nobody else could get those back: a fresh clone builds B, gets other bytes, and the pin is lost. And run could not fix it, because run moves no pin. So the pin is removed, update says “let go”, and the next run builds B and pins it. The rule is unchanged for a path dependency, and for a git one whose commit did not move.

Known gaps in 4a.

  1. Pinning still reads the folder. For a path dependency, pin and update copy what is there at that moment, and pin hashes it to say what has changed. Run while its owner is half-way through a rebuild, update pins the half-built state. Snapshots (4b) close it.

  2. Refreshing a git dependency’s data takes two commands: chartbook run --force builds it again, and the pin does not move until chartbook update.

  3. Nothing clears old working copies. A branch that moves leaves one per commit, each with whatever its build wrote. chartbook store gc does not touch the git cache.

  4. Two runs at once in one working copy are not kept apart. Two projects of one user that depend on the same commit share it.

  5. A path dependency of a git dependency is not built, and is looked for beside the working copy, where it almost never is. That dependency’s build stops at its pin.

  6. On a first run, a git dependency is fetched twice: once to choose the commit to build, once by the pin. If the branch moves in between, the pin lands on a commit that was not built, and says “not built”. The next run builds that commit and pins it.

  5. “chartbook update — move pins forward to current upstream state, and rebuild what that invalidates.” (Design: the asset graph.) update rebuilds nothing; the pair is update, then run.

  6. “chartbook run pins anything not yet pinned, so neither verb is needed to get started.” True as built, for build. Any other script pins nothing.

  7. “build still means ‘render the website’ and keeps doing so until run exists; the rename is one breaking change, made once, in the same release as run.” (Design: the asset graph.) run exists and the rename is 4c. The two do not fit: one build makes all of a pipeline’s assets. The snapshot settles it as one record for a pipeline at a commit, naming each asset’s hash.

Seen while trying it by hand. A pin is read-only (decided in 3d). A build script that copies a pinned file with cp gets a read-only copy, and cannot write over it on the next run. Nothing is wrong, and it will surprise someone. Reading the pinned file in place avoids it.

Proposed: implemented in 4b, and waiting on the maintainer’s yes.

  1. The command is chartbook snapshot, run in the pipeline, with no argument.

  2. “Everything committed” means the pipeline’s own folder. A changed, staged, deleted or new un-ignored file there is refused, and listed. What git ignores does not count, which is how built data stays out of it. Other work in the same repository does not count either, so one agent’s half-finished change does not hold up another pipeline’s snapshot. The cost: a pipeline that imports code from elsewhere in its repository can be given a label that uncommitted work elsewhere makes untrue.

  3. A snapshot is found by commit and by the pipeline’s folder in its repository, not by the pipeline’s name: snapshots/<commit>/<folder>/<time>.json. A commit is the same in every clone, so nothing needs to agree on a name.

  4. A path dependency follows the branch its folder is on. pin and update take the newest snapshot at the commit the folder is on or, if that commit has none, at the nearest commit before it that has one. Its owner can be several commits past the last build they declared ready. A snapshot made on another branch is not found.

  5. One commit can have several snapshots, told apart by the time they were made, to the microsecond. The newest is the one a pin moves to. Making one when nothing has changed since the last at that commit makes none.

  6. A dependency is pinned to one snapshot, whole. pin does not take one asset from a newer snapshot and leave the rest. This replaces, for a path dependency, 3c’s “pins what has no pin yet: an asset the other pipeline has started to declare”.

  7. pin says what a newer snapshot would change, and stays. It no longer hashes anything to find out: it compares two records.

  8. update drops what the newer snapshot no longer declares, and lets go of what it did not build. The second is the rule of 4a’s number 19, for the same reason.

  9. An asset that is declared and not built is in the snapshot without a hash, and the rest is in it all the same, as pin already did. A pipeline that has built nothing has no snapshot to make.

  10. The lockfile names the snapshot: its commit in location.commit, where a git dependency’s commit already is, and its time in snapshot. So the lockfile says which code as well as which data, for both kinds of dependency. The index carries both.

  11. With no snapshot, nothing is pinned, and the message says what the owner has to do. chartbook run stops there, before the build.

  12. The record is JSON in the index’s format, like the lockfile, with its own schema.

  13. A snapshot’s files are stored as a pin’s are: a copy-on-write clone or a copy, never a link to the pipeline’s own file.

  14. chartbook store gc never removes what a snapshot names, whether or not anything pins it yet. A record that cannot be read stops the clearing.

  15. The buried option is --from-folder, on pin and update, hidden from --help. It does what both did before 4b. The lockfile then names no commit, and a plain update afterwards moves back to a snapshot. Removed 2026-10-17, by decision 4 of Design: reading another pipeline while you work: a lockfile never records a read of a working folder.

  16. Looking at a repository takes no lock (GIT_OPTIONAL_LOCKS=0), so finding a snapshot never gets in the way of whoever is working in that folder.

  17. builds/ in the store stays a name that is kept free. Records go in snapshots/.

Known gaps in 4b.

  1. A snapshot takes its owner’s word. It records what is on disk as what the commit built. If the owner changed code, committed, and did not rebuild, the label is wrong and nothing notices. (Closed the same day for chartbook run --snapshot, which builds first: “4b, continued”, below. chartbook snapshot by itself still takes its owner’s word, and the record says which of the two made it.)

  2. Nothing clears old snapshots. Each is its own copy of the files where the disk has no copy-on-write clones, and the store grows with each one. (Closed 2026-10-13: “Clearing old snapshots”, below.)

  3. A snapshot is on one machine. A colleague, or CI, has none of them. For a path dependency they make their own in that folder. A shared store is the answer, later. (Closed 2026-10-14: “4g, as built”, below.)

  4. A lockfile from one machine cannot be put back on another for a path dependency unless the same bytes are built there. pin reports a pin whose bytes are not in the store as lost.

  5. chartbook check reads a dependency’s manifest from its folder, as it stands, to see that it declares what a model was trained on. It should read it at the pinned commit.

  6. A git dependency does not use a snapshot. If its owner made one at that commit on this machine, chartbook run still builds the commit again in a clean copy.

  7. The examples need a clean folder. cd examples && doit makes a snapshot of yield_curve, so it fails, and says why, if that example has been edited and not committed.

Where the design was wrong, or said less than it seemed to.

  1. “Keep the boring files. path stays the real location where a parquet file lives, and the store is a cache that links into it.” (Design: the asset graph, “The store”.) For the pipeline’s own folder, still true. For what others read, the store is not a cache: it is the only place they read from.

  2. “A cache and a pin are not the same thing … a pinned object is reachable and must never be collected, while an unreferenced build result may be.” (Design: the asset graph.) A snapshot is a third thing: nothing pins it yet, and it must not be collected, because it was declared ready on purpose.

  3. The store’s two indexes: “the build record maps input hash → output hash”. (Design: the asset graph.) What was built maps a commit to output hashes. The commit is the input that people can name and check out; an input hash over code, parameters and tools is not built, and the model does not need one.

  4. “pin puts back what the store has lost, when the other pipeline still has the same bytes” (3c, proposed 5). For a path dependency it no longer can, because it does not read the folder. A snapshot is what puts bytes in the store.

  5. “pin hashes what is already pinned, to say what has changed upstream” (3c, proposed 6), with its note that a remembered hash would make that cheap. For a path dependency there is nothing to hash any more.

Proposed: implemented, and waiting on the maintainer’s yes. All of it; the maintainer asked not to be consulted on rules of this size.

  1. A snapshot is kept if a lockfile pins it, if it is the newest of its pipeline or the newest a branch or tag can pin from, if a label points at a model version in it, or if it was made in the last 30 days. Otherwise it may be removed. The rules are tried in that order, and the first that holds is the reason the command gives. (The branch rule was added by the third review, below: pin chooses by commit ancestry, so a release branch’s last snapshot is what its users pin, and the plain “newest” would have removed it.)

  2. Thirty days. Long enough to come back from a holiday to; short enough that a nightly build does not fill a disk. --keep-days moves it, down to zero.

  3. “The newest of its pipeline” is by pipeline ID and folder within its repository, which is what the store can tell without a repository to hand. A pipeline that renames itself becomes two pipelines to this rule for as long as both have snapshots.

  4. The store notes where a snapshot was made from, in a file origins beside the pipeline’s records at that commit: one repository folder per line. It is not a record, has no .json, and is not shared. It is how gc finds the manifest whose labels say which versions to keep.

  5. Labels are read from that manifest as it is now, committed or not. A label is what someone is relying on now. A folder that is gone, or a manifest that cannot be read, says nothing, and the other three rules still hold. (Since 2026-10-14 the newest snapshot’s own record of its labels counts too, for a folder on another machine: “4g, as built”, below.)

  6. A lockfile that cannot be found keeps any snapshot that holds an object it named. That is as much as is known about it.

  7. Removing a snapshot removes its record; its objects go by the existing rule, in the same run, when nothing else names them. An object stored in the last hour is spared, as before, so the run that removes a record may leave its objects for the next.

  8. The last record at a commit takes its folder and its origins note with it.

  9. Nothing is removed if any record cannot be read, as for a lockfile.

  10. The plan is made again when the yes comes, and only what both plans say may go is removed. A pin that landed while someone was deciding is honoured. (Third review.)

  11. A label shorter than a version’s name keeps nothing. champion = "" would otherwise match every version. Only what [models.x.aliases] accepts, twelve or more hex digits, is read. (Third review.)

  12. The last record at a commit leaves a half-written one alone. Only the origins note goes with it, and the folder if it is then empty. (Third review.)

Known gaps.

  1. A label in a manifest that was never a snapshot’s origin is not seen. A clone that pins nothing and makes no snapshots can label a version that gc on this machine then removes. chartbook check there says the version is not on this machine.

  2. Git working copies are still never cleared. ~/.chartbook/git/work/ grows by one copy per commit built.

Where the design said less than it seemed to. “A recorded version is reachable, so chartbook store gc never collects it.” (Design: models.) Every version would then be kept for ever, and Design: models itself lists retention as an open question (“a model retrained nightly makes 365 a year … probably a per-model keep = N”). As built, a labelled version is kept and an unlabelled one goes with its snapshot after 30 days, which answers the question without a new field.

What two adversarial reviews found, and what was done#

Added 2026-10-13. After the step 4 pull requests were merged, two sub-agents reviewed main with no knowledge of the builder’s conclusions: one for correctness and races, one for safety. They found twenty-six things between them. Each is in the changelog under “Fixed”, and the ones that change a rule are here.

Changed rules, all proposed.

  4. The recursion guard sees the whole chain of scripts, in CHARTBOOK_RUN_STACK, and comes before the pin.

  5. A version is found at any commit the repository still has, asked of git’s object store, so an amended-away commit keeps its versions until git prunes it.

The third review read the two commits of this pull request before they were merged, and found twelve more.   • A snapshot that takes over an hour to store can lose an early object to a concurrent gc. Improbable; a store-wide lock is the fix, and is not built.

  • A shallow clone cannot see snapshots beyond its depth, and the message blames the owner.

  • chartbook init renders whatever is on main, not the installed version; needs tags.

  • No timeouts on git calls. Prompts are off; a GUI credential helper could still block.

  • A lockfile that cannot be found keeps the snapshots its note recorded, for as long as it is missing (since 2026-10-17; a note from before keeps the newest snapshot holding each of its objects). The command points at --forget-missing.

What --frozen checks. The lockfile exists if the manifest has dependencies; every dependency in the manifest is in the lockfile, and the other way round; a dependency is pinned from where the manifest now says it is (_declared_elsewhere); each has something pinned; each asset has a content hash, that is, was built when it was pinned; and the store has every hash. It opens no repository and uses no network. run --frozen skips the pin and the building of git dependencies, runs verify() in their place, and refuses to build on a problem. Since 2026-10-17 it leaves, where the store can be written and not under CI, this machine’s note of the lockfile for store gc, so that a machine that only reads keeps what it reads; it writes no lockfile and no object.

Proposed: decided here, not by the maintainer.

  1. An asset not built when it was pinned is a problem under --frozen. pin records it and goes on, so that an upstream with one dataframe behind a subscription is still usable; the design said the stricter choice is what --frozen is for, and this is it.

  2. --frozen is a flag on pin and run, not a command, and not on check. check never reads the store or the lockfile; keeping that so is the reason, and the open question above asks whether CI would rather have one command.

  3. Labels travel with snapshots. A snapshot records the model versions its manifest’s [models.x.aliases] named when it was made, and gc reads the newest snapshot’s as well as the folder’s manifest. So a label given on one machine is known to a gc on another, as of the newest snapshot; and only the newest counts, so that a label taken away releases its version once a snapshot follows (a second review found the first version of this read every snapshot’s labels, which kept a version for ever). The first design here kept every snapshot whose folder this machine cannot see; the first review found that a CI runner’s checkout is such a folder the moment the job ends, so that rule would have kept every nightly snapshot for ever, and it was replaced by this. What is still not known across machines: a label given after the newest snapshot, and which snapshot a branch tip on another machine pins from.

  4. A read-only store is a note, not a failure, for a path dependency pinned from a snapshot. The only write that pin needs in the store then is the root note for gc; so the store’s owner is the one who runs gc, and a pin that could not leave the note says so once. Only a permission error is treated so; a disk that is full is still an error, and a half-written note is removed. What has to write the store (a git dependency’s first pin, --from-folder, snapshot) stops with a message that says the store is read-only and what to do.

  5. Nothing new in the store’s layout. Sharing is a path in settings.toml, which existed. Snapshots were already the store’s own bytes (snapshot.LINKS is reflink then copy), which is what makes a shared disk work; it is recorded here because it was found, not made.

What an adversarial review found before merge (2026-10-14; eleven findings, each fixed with a test unless said otherwise): the gc rule above, which would have kept every CI snapshot for ever (replaced); “a read-only store still pins” was true only for a path dependency from a snapshot, and a git dependency’s pin failed with a bare errno (the message now says the store is read-only and what to do; the docs say which pins write); every OSError from the gc note was reported as “read-only”, so a full disk passed silently and left a half-written note (the catch is permission errors only, the note is whole or not at all); run --frozen skipped verify() when the manifest had no dependencies, although the lockfile might still list one, and --frozen on a non-build script was ignored (both fixed: run --frozen always verifies; a non-build script with --frozen is refused); verify()‘s remedy for a pin the store lacks said chartbook pin, which never re-stores a path dependency’s lost pin (the remedy now depends on the kind); --forget-missing on a shared store discards other machines’ pins and nothing said so (the help, the hint and the docs do); the store gc reference and docstring listed the old rules (updated); the read-only note was wrong on the remove_root path (reworded); the read-only test only chmod’ed roots/ (a fully read-only store is tested, from a snapshot); a lockfile entry without an id was a KeyError (a LockError with a remedy); a docstring’s rule numbers.

A second review, of those fixes, found seven more, all fixed: labels recorded in any snapshot kept a version for ever, even after the owner took the label away (the newest snapshot’s labels count, and no other’s); chartbook snapshot on a read-only store still printed a bare errno; the remedy for a lost pin was wrong for a --from-folder pin, and its test asserted the wrong remedy (it depends on the kind of pin now: repository, snapshot or folder); a full disk after the lockfile was written lost the report (a LockError says the lockfile was written and the note was not); run --frozen on a leaf pipeline said “0 pin(s) of 0 dependencies” (“no dependencies to check”); the snapshot record’s labels was in no schema and no table; the store gc docstring left out the branch-tip rule.

Known gaps. A shared store is cleared by its owner, from the machine the snapshots were made on, and without --forget-missing: another machine’s lockfile cannot be found from here, so a writable roots/ is what lets its pins be known, and a label given after the last snapshot, or a branch tip on another machine, is not known at all. The origins note and the roots note hold paths from the machine that wrote them. A lockfile does not say which store its pins went into; --frozen checks the store this machine is pointed at. Concurrent writers to a shared store rely on each file being written whole and then renamed into place, which is what the store does; nothing locks the store as a whole.

How it is judged. Proposed: decided here.

  1.   2. Keyed as the lockfile keys assets: a local input by its name, another pipeline’s by the dependency’s key, so the two sides of the comparison line up without a resolver.

  3. Out of date is a warning in check, not a problem. A model may be kept on purpose, and retraining is the pipeline’s build to run.

  4. A retrained model that has no snapshot yet says nothing, rather than “up to date”: its bytes are no version, so there is nothing recorded to compare with. The snapshot that follows makes it one.

The comparison is as good as the snapshot’s record: a model whose version predates this change has no trained_on and is never out of date. A version is its bytes: a model retrained to the same bytes on new inputs is the same version, keeps the inputs it was first made with, and is reported out of date although retraining changes nothing. A dependency whose key in [dependencies] is renamed after the version was made has the old key in trained_with and no match in now, so nothing is said of it. staleness() hashes the model file and its local inputs again, without the index’s cache, and reads every snapshot of the pipeline once per model, in the index and in check. A git dependency’s input is compared by its pinned hash like any other.

Proposed: where the design was silent or is departed from.

  1. Cross-pipeline references work in data.sql() and data.ref() for file dataframes, as the pinned copy. The design put that in a later phase; the resolution chain exists, so it costs nothing. A table or query of another pipeline was not pinned at first (a snapshot holds files); since 2026-10-15 the snapshot writes it out as parquet into the store, so it is pinned and read across pipelines like a file. The gap is closed in that simple form.

  2. A query names one source.   3. duckdb is a dependency of chartbook, not an extra, by the one-install rule.

  4. A url with credentials in it does not load. The design said “no credentials, ever”; the loader enforces it.

  5. An unknown backend is refused by name. No plugin seam yet: DuckDB is the second implementation after parquet, and the rule is three.

  6. data.load() of a table or query returns a LazyFrame that DuckDB backs. A file is opened afresh for each load; the frame keeps its connection while it lives.

  7. The default policy’s path requirement is met by a table or a query. The rule asks where the dataframe is; a source answers.

  8. check reports a DuckDB file that is not built, and skips that with --skip-outputs, as for any output. It does not connect.

  9. The page is read from the engine when the site is built: columns, row count, first five rows. A source that cannot be read gets a page that says so.

What an adversarial review found before merge (2026-10-13; fifteen findings, each fixed with a test unless said otherwise):

  1. The credential chain, source_url(), was documented everywhere and called nowhere: the manifest’s URL was what opened every source. The loader now resolves each source through it, refuses a machine URL for another engine, and the index records the manifest’s URL only.

  2. A query that bound but failed when run (a cast that fails on one value) aborted the whole site build; describe and count(*) had both passed. The page now says what happened and the site is built. Such an error carries DuckDB’s message; whether Polars wraps it as ComputeError or lets DuckDB’s exception through depends on the Polars version (CI’s newer Polars did the second), so the page catches Exception and the docs promise the message only.

  3. One in-memory connection was shared by every :memory: source and by files-only data.sql(), so a table a user made through connect() showed up in SQL over files. Files-only SQL now runs in a fresh engine of its own; a :memory: source is one writable connection, by nature, and the docs say so.

  4. A query spliced as (sql) broke on a trailing ; or -- comment; it is (\nsql\n) now, with the semicolon dropped.

  5. A table or query of another pipeline was reported as “had no dataframe named … update pins it”, which was false. It now says it is a table in a source and cannot be read across pipelines yet. The catalog’s two-argument path blamed a missing path; it resolves the table.

  6. A query with a newline or a | broke the manifest table on its page; the SQL is in a fenced block below it now.

  7. {'a': 1} and '{x}' in data.sql() were read as references; a doubled brace is a literal.

  8. A connection kept for the process read stale data after a rebuild and held the file’s lock. A file is opened afresh for each load; a frame keeps its own connection while it lives, which is the lock’s true scope, and the docs say to drop it before rebuilding.

  9. duckdb>=1.1 was below .pl(lazy=True), which arrived in 1.4; the floor is 1.4, and polars 1.20 for the IO-plugin seam it uses. No test: every environment has a newer one.

  10. duckdb://host/x became a folder, ?options part of the file’s name, and user@ passed. A DuckDB URL is a file and nothing else; the rest is refused with a reason.

  11. A typo in table left the record silently without columns; the index warns.

  12. The page’s first and last dates were None for a table with a date_col; the engine is asked for min and max.

  13. path = "" with a source passed as a file; presence is tested, not truthiness.

  14. definition_hash left out the source, so the same table name in two sources hashed alike.

  15. Test hygiene: the dtype in the index test is pinned, and the tests no longer reach into a connection cache, since there is none.

Known gaps. A table or query is not pinned and not in a snapshot, so it is not reproducible across time or pipelines the way a file is. Only DuckDB. One source per query. A DuckDB file is opened read-only, which a user can get round with their own duckdb.connect; ChartBook does not police the engine. A column of a DuckDB UNION type makes .pl(lazy=True) panic inside DuckDB (a BaseException), which nothing here catches.

Step 6. Readers of the index#

Once the index is stable: render the site from it, a Dagster export, an MCP server, a provenance panel on each page, a diff of two indexes. Each is a reader of one file (Design: the index, “What this unblocks”).

Direction, decided by the maintainer 2026-10-14. The four documents stay as they are: manifest, lockfile, snapshot, index (Vocabulary). The lockfile is never merged into the index: it is an input to a build and the index is its output, it has no timestamp on purpose so that a diff of it means “a pin moved”, and it stays committed; the index reports pins and never makes one. The pair that converges is snapshot and index: a snapshot is one pipeline’s index at one commit, kept with the bytes; a site’s index is its own pipeline at the current build plus each dependency’s pinned snapshot plus the catalog; a site is a pure function of an index and the write-ups at the commit the index names, so a site can later be built for any snapshot and lineage can link across sites by commit. That is a direction, not work for now. Superseded 2026-10-16 by Design: the versioned catalog: the two do not converge; a snapshot holds the index of its version, and a catalog will be assembled from such indexes. The index records facts about the build, including comparisons it made, and no renderings; each asset record is to gain its write-up’s path and hash; stale_inputs stays. A writer per site tool turns the index into pages; the Sphinx writer comes first, after a vocabulary page and an inventory of what every page shows today; MkDocs and Next.js writers are the roadmap’s reason to keep the index clean. The inventory of what every page shows, and what the index must gain for a writer to show it, is Design: the writer, and what every page shows; the five facts it found missing were added the same day (6c): each write-up’s content_hash, modified_at on file locations, date_range on a dated dataframe, code_changed_at on the pipeline, and the policy, which the catalog record already carried.

6a. A diff of two indexes — as built#

Added 2026-10-14. The smallest reader, and the one a reviewer of any build wants: chartbook index diff BEFORE AFTER says what changed between two builds from their index.json files alone. chartbook/indexdiff.py; tests/test_index_diff.py.

Proposed: decided here. The two indexes are compared as published (index.published() applied to both), so a build directory’s full index and the site’s compare as equals and no local path is ever in the output; generated_at is ignored. Records are matched by kind and ID. A changed record is described in words a reviewer uses, worked out from which fields differ: data changed for a content or definition hash, size, row count, columns or files; pins moved for a pipeline’s dependencies; N new version(s); labels moved; out of date or up to date again; scores changed; else declared differently with the field names. The hashes and row counts are printed for data. --json gives every changed field before and after; --exit-code exits 1 on any difference, as git diff --exit-code does. The index was judged stable enough for this: the diff reads only kind, id and whole fields, so a field added to a record later shows as declared differently and breaks nothing.

What an adversarial review found before merge (2026-10-14; eleven findings, each fixed with a test unless said otherwise): a Plotly chart written without a fixed div_id embeds a fresh id on every render, so every chart’s content_hash moved on every build and --exit-code would have fired for nothing (ChartBook’s plotting helpers, the examples and the template pass a div_id now; a chart’s change reads rendered differently; the docs say what to do in one’s own code); the reference’s example output could not be produced (a pipeline’s assets changes with every asset added; the example shows it); declared differently was said of fields nobody declared (assets, pinned_inputs, trained_with, inputs, location have words of their own); the inputs out of date were cut at sixty characters (lists are printed whole); a different root or schema was silent (said first); pins moved fired for a dependency relocated with no pin moving (it reads the pinned hashes); a malformed record crashed (refused with a message); dead label parameters on format_diff() (gone); the model fields read from the local store make two machines’ indexes differ for no change (not fixed; said in the docs); a test comment was false and an assertion passed for the wrong reason (fixed; Pipeline wording, a folder without index.json, a columns-only change and the envelope are tested); versions changed did not tell a version lost from one replaced (new and gone are counted and named).

Known gaps. A record whose ID changes (a renamed asset) is a removal and an addition, not a rename. An executed notebook’s HTML carries ids and times from its run, so its hash moves on every render and the diff says rendered differently of it, as of a chart; the live example site showed this. A Series record follows its dataframe and is listed on its own. A model’s versions, trained_with and stale_inputs are the building machine’s. Nothing yet fetches the before index from git or from a deployed site; the reviewer brings both files.

6b. The provenance panel — as built#

Added 2026-10-14, by the maintainer’s choice of what to build next. Every dataframe, chart and model page carries a Provenance section, before its manifest sections: what this is and where it is; its content hash, size, rows and columns, or its definition hash; which pipeline built it and with what script; what it was made from, at which hash, pinned from which snapshot of which commit, and whether that has moved since the model was trained; what is made from it; and, for a model, which version the file is and its labels. chartbook/provenance.py, panel(); the include provenance.md in both themes; tests/test_provenance.py.

Proposed: decided here.

  1. The pages are readers of the index. The build makes the index first, once, in build_docs, and hands the records to the page generators; a page’s panel is panel(record_id, records), which reads the index and nothing else. The same index is written beside the site at the end. An incremental build mixes into each pipeline’s fingerprint a digest of what its panels would say (provenance.digest()), since a panel reads other pipelines’ records: an upstream rebuilt, or a new chart made from this dataframe elsewhere, regenerates every page of each pipeline one of whose panels would change, and no other pipeline’s. This is the first step toward rendering the site from the index, which the maintainer wants to discuss before it is built: a page already carries one section written from its record.

  2. Facts, not links. The panel names assets by ID in code, and does not link them; the pages’ existing sections link. A link scheme that works for both themes belongs to the site-from-index design.

  3. The panel is the record’s. Nothing in it is computed from a manifest or a file; what the index does not have (a pipeline’s own commit, a build time) the panel does not say. Those are the Build records the index design leaves for later.

Decisions by the maintainer, 2026-10-14, on the other readers. An MCP server is an idea for later, filed as GitHub issue 54, not to be built now. Rendering the site from the index is to be discussed very soon and is not to be built before that conversation. A Dagster export is not wanted at all for now.

What an adversarial review found before merge (2026-10-14; six findings, each fixed with a test, the single index build included, which a test now counts): in an incremental build a reused pipeline’s pages kept panels that had read other pipelines’ records, so after an upstream rebuild the page disagreed with index.json (the index is built once, before the plan, and each pipeline’s fingerprint carries a digest of what its panels say); a build script with a | in it broke the panel’s table (cells are escaped); an input pinned and also in the site said nothing when the live upstream had moved on since the pin (it says “now at …”); the docs said a page “ends with” the panel, which the manifest sections follow (reworded); the index was built twice per build, and what the hash cache does not cover (parquet footers, DuckDB describes, versions, staleness) ran twice (once now); the model page, the catalog theme and the incremental path were tested only on hand-made records (a two-pipeline catalog is built, rebuilt incrementally and checked). A second review found five small things, fixed: the salts were quadratic in the size of the index (a reverse map is built once per index, and serves every page too); the whole index was built before a build directory holding unrelated files was refused (refused first); two wordings; and the test now counts the index builds and asserts the salt-driven regeneration.

Known gaps. A panel says nothing of a pipeline’s own commit or of when the build ran: the index has no Build record yet. An input not in the site (another pipeline’s dataframe, when the site is one pipeline’s) is named and shown at its pinned hash only. The Pipeline page has no panel; its dependencies’ pins are in the pipeline manifest section already.

Working in the code#

The contributing guide (Contributing) has setup and style. These are the things that are easy to miss:

  • Run tests with hatch test, not pytest directly. hatch test --all runs six environments (Python 3.10 to 3.13, and Sphinx 7 and 8 on 3.13), and all six must pass.

  • Build the docs with hatch run docs:build. One warning is expected, about a plotly MIME type in gallery.ipynb. Any other warning is yours.

  • A new module needs a line in docs_src/reference/api.md, or the docs build warns.

  • The index is a contract. A change to what chartbook/index.py writes needs the same change in Design: the index and in the JSON Schema for that record, in one commit. A change to how anything is hashed needs a new algorithm prefix.

  • Every user-visible change needs a changelog entry in docs_src/changelog.md, in paragraphs that say why. A breaking change is marked breaking and says what to do instead.

  • The agent skill is in two places. Edit src/chartbook/skills/, then copy to .claude/skills/chartbook/. Update llm/llms.txt and llm/llms-full.txt when commands change.

  • The examples are tests. cd examples && doit must build both example pipelines and the catalog, and chartbook check must pass on each. They pull live data and need a FRED API key in a git-ignored .env; never print or commit it.

  • Do not edit a design document to match what you happened to build. If the design is wrong, change the design on purpose, say why in the document, and get the maintainer’s agreement. Mark what is decided and what is proposed, as Design: models does.

  • Commit messages explain why, in paragraphs.
